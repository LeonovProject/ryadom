# Рядом

BE-P2 и FE-P2 объединены: [результат и снимки](docs/development/integration/2026-10-20/p2/README.md).
Работают запись, личные встречи/главная, принятие и отказ, обсуждение;
API модерации скрывает сообщения и снимает встречи. Совместные S3/S4/S5 и
сохранность проверены; административные формы FE-11 ещё впереди. Следующие
BE-10–12 и FE-11–13. Локальный просмотр: http://127.0.0.1:4180/.


По решению пользователя работа теперь идёт [пакетами по 2–3 карточки](docs/development/handoff/work-packets.md):
после принятых P1/P2 следующие BE-10–12 и FE-11–13; FRONTEND подключает экраны своей стороны,
BACKEND — свои модули. Интеграция после пакета, повтор проверок по необходимости.

BE-03 интегрирована: [каталог и чтение встреч](docs/development/integration/2026-10-20/be-03/README.md)
доступны через общий API/preview. Последующее создание/организации уже приняты
в пакетной интеграции, указанной выше; отчёт BE-03 сохранён как история.

Общая точка продолжения раздельной работы —
[передача от 20 октября](docs/development/handoff/continuation-2026-10-20.md).
В ней результаты исходной передачи и интеграций P1/P2, границы общих файлов
и порядок обновления веток. Оба исполнителя используют SHA этой передачи.

Подготовлены спецификации двух улучшений для отдельной реализации:
[помощник условий первой встречи](docs/product/first-meeting-helper.md) и
[печатное приглашение с QR](docs/product/printable-invitation.md).
[Задания агентам](docs/development/tasks/first-meeting.md) определяют файлы,
зависимости и приёмку. Функции ещё не реализованы; API/БД остаются прежними.

Платформа для совместных занятий разными видами спорта по кейсу Столото.
Расширение на другие активности — идея команды для развития.
Рабочее название — «Рядом». Веб планируется на React; мобильное приложение —
собственная идея команды, для которой рассматривается React Native.

В локальной реализации готовы серверная основа BE-01, SQL-схема DB-01,
криптография AUTH-01, демонабор DB-02 и общий SVG-валидатор MEDIA-00.
[OPS-01](infra/README.md) добавляет общий запуск web/API/PostgreSQL, миграции,
явный seed, постоянный том, proxy и HTTPS. В main объединены коммиты
`f4ef6a5` бэкенда и `6d1dab9` фронтенда (FE-01–07).
[Отчёт интеграции и снимки](docs/development/integration/2026-10-20/README.md)
содержат проверенное поведение, ограничения и следующие задания.
Локальный просмотр: **http://127.0.0.1:4180/**; Swagger: **http://127.0.0.1:4180/api/docs/**. [BE-02](apps/api/internal/modules/auth/README.md) реализует настоящий вход,
регистрацию, выход, текущий/публичный аккаунт и каталог аватаров. Этот путь
проверен через HTTPS и форму веба. BE-03 добавляет направления, каталог,
карточку и собственный список встреч; BE-04–06 — создание/организации/допуск.
Участие и обсуждение приняты в P2; остальные административные и медиа-модули ещё впереди. [Пакет передачи разработчикам](docs/development/handoff/README.md)
фиксирует владельцев, версии, проверки и первые задания. Для бэкенда утверждены **Go, chi,
PostgreSQL, pgx/sqlc и goose** — [решение ADR-001](docs/architecture/backend-decision.md).
[Контейнеризация Docker Compose](docs/development/containerization.md) обязательна
с первого этапа. Клиентская основа и версии закреплены в
[ADR-002](docs/architecture/foundation-decision.md); команды проверки BASE-01 —
[в пакете передачи](docs/development/handoff/README.md). Команды запуска основы —
[в инструкции OPS-01](infra/README.md); пользовательские сценарии ещё впереди.
S3 исключён: личные [SVG-аватары с модерацией](docs/product/avatars.md) и SVG-фоны —
строки в PostgreSQL после серверной проверки, максимум **128 КиБ (131 072 байта)**.
Предусмотрен также выбор готовых SVG из общего каталога: они не требуют
повторной модерации. В [каталоге](packages/contracts/avatar-presets.json) уже есть
аватар «Спутник»; подготовлен также SVG-фон «Точка встречи».
[Стартовые изображения и подключение](design/assets/README.md) — DEC-22; ожидание файлов снято.
[Регистрация](docs/product/registration.md): email, пароль, имя и обязательный готовый аватар
на одной странице; свой SVG можно загрузить позже в профиле.
Даже единственный вариант выбирается явно. Проверка случая пустого каталога
сохраняется: он блокирует новую регистрацию, но не вход существующим аккаунтом.
В MVP предусмотрен [сброс БД к сиду из аккаунта ADMIN](docs/product/demo-reset.md):
подтверждение, атомарное восстановление и завершение всех сессий.
По [DEC-20](docs/architecture/authentication.md) приняты email/пароль и JWT-cookie
с серверным отзывом; подтверждения почты/восстановления пароля в MVP нет.
[DEC-21](docs/product/account-blocking.md): ADMIN блокирует USER с отзывом всех
сессий, сохраняя контент/участие/допуск. Вход уже работает; административная блокировка, личные SVG и демосброс
ещё не реализованы.
По [DEC-14](docs/product/home-proposal.md) личная главная показывает сначала
будущие подтверждённые встречи, затем компактно начавшиеся сегодня. Серверные
окна/сортировка до пагинации описаны в контракте; макет пока не изменён.
По DEC-15/16 раздел «Участвую» открывается с предстоящих; начавшиеся/все записи
доступны отдельно. Вход/регистрация без returnTo ведут на персональную главную.
DEC-17 сохраняет весь согласованный объём до сдачи. DEC-18/19 уточняют последние
сообщения с загрузкой ранних и фильтр календарных дат в зоне каждой встречи. [Проверка согласованности
работ](docs/product/readiness-review.md) описывает исправления очереди и внешние зависимости.

Для параллельной разработки подготовлен **[контракт API 0.13.0](docs/contracts/api-v1.md)**:
[OpenAPI](packages/contracts/openapi.yaml), 280 HTTP-примеров и проверка генерации
для Go и TypeScript. Вход/аккаунты реализованы в BE-02, чтение встреч/направлений — в BE-03;
BE-04–09 добавили создание/организации, участие/обсуждение и API модерации;
дальнейшие операции ещё в очереди.
После разработки на адресе прототипа обязательны Swagger UI `/api/docs` и файл
`/api/openapi.yaml` — [требование к API-документации](docs/development/api-documentation.md).
Эти маршруты уже включены в веб-образ и проверены локально. Внешний адрес
проверяется после самостоятельного развёртывания пользователем.

[Последние решения пользователя](docs/product/decisions.md): запись и решения
по заявкам закрываются в момент начала; время показывается в зоне встречи.
Принята [модерация справочника направлений](docs/product/activity-types.md):
одобрение, отказ с причиной и исправление имени; свой спорт используется сразу.
Приняты [жалобы на встречи и сообщения](docs/product/reports-and-moderation.md):
ручной разбор без причины жалобы, восстановление скрытого сообщения.
Сдача — **20 октября 2026, 23:00 по Красноярску (GMT+7)**. Сервер у пользователя
уже есть; он самостоятельно развернёт готовую контейнерную поставку.

По [DEC-24](docs/development/delivery-brief.md) до 23:00 фиксируются последний
коммит и презентация — пользователь берёт это на себя. Защита командой: **8 минут**.
Машина/интернет предоставлены, доступы GitVerse уже настроены. Акцент —
популяризация спорта, в том числе среди старшего поколения.
[Демодоступы](docs/product/demo-access.md): `/demo`, скачиваемый `/demo/accounts.txt`
и подстановка в форме входа. Для включения задать `WEB_DEMO_ACCESS=true` и
пересобрать web; настоящий вход и серверные права сохраняются.

## Дизайн-прототип

По DEC-26 выборочно применён коммит 9120106 из origin/kirill: SVG-иллюстрации,
выбор обложки и просмотр допущенных организаций без членства.
[Разбор и снимки](design/reviews/2026-10-20/README.md) описывают исправления,
отклонённые части и отличия от реального React-приложения.

Локальная версия **0.3**: [открыть HTML-макет](design/prototype/index.html),
[инструкция просмотра](design/prototype/README.md). В нём 18 исходных
маршрутов, включая кабинеты организаций и модерацию, плюс экспериментальный
`#/orgs` (всего 19). [Покрытие](design/prototype/coverage.md)
описывает состояния и связные пути. Все данные вымышлены, изменения сбрасываются
при перезагрузке. Это макет дизайна, не работающий продукт.
Административные маршруты SCR-20/21/22 добавлены в карту по DEC-07/09/21,
но ещё не включены в макет 0.3: карта приложения содержит 21 основной URL
и общие состояния SCR-19. EXP-01 не занимает SCR-20.
Демовыбор профиля в макете устарел: для приложения принят обычный вход email/паролем.
Визуальный проход во встроенном браузере выполнен: все 18 экранов на компьютере
и телефоне, ключевые — на 320/768 px. [Отчёт и снимки](design/reviews/2026-10-19/README.md)
содержат найденные дефекты, исправления и ограничения проверки.
[Повторная проверка экранов](docs/product/screen-review.md) описывает исправления,
недостающие состояния и развитие макетов.

## Начать работу

1. Прочитайте [инструкции агентам](AGENTS.md).
2. Изучите [границы продукта](docs/product/scope.md) и
   [первичные источники](docs/requirements/README.md):
   [постановку](docs/requirements/assignment.md) и
   [критерии](docs/requirements/evaluation-criteria.md). Сверяйте сценарии с
   [приёмкой](docs/product/acceptance.md).
3. Для параллельной работы используйте
   [порядок координации](docs/development/multi-agent-workflow.md) и
   [очередь областей](docs/development/backlog.md). Исполнителям назначаются
   [небольшие карточки](docs/development/tasks/README.md) по одной, с проверкой
   зависимостей и последующей интеграцией.
4. До разделения реализации согласуйте [общие контракты](docs/contracts/README.md).
5. Для обсуждения реализации прочитайте [технический проект](docs/architecture/README.md),
   [модель данных](docs/architecture/data-model.md), [проект API](docs/contracts/api-proposal.md)
   и [план работ](docs/development/implementation-plan.md). Бэкенд и контейнеризация
   утверждены в ADR-001; DTO/права/переходы зафиксированы контрактом API 0.13.0.
   Наличие документов не означает разрешения начинать разработку.
6. Состав страниц и их содержимое — [карта экранов](docs/product/screens.md),
   переходы между ними — [пользовательские пути](docs/product/user-flows.md).

## Проверки репозитория

Без сторонних зависимостей, Python 3.10 и новее:

```bash
python3 scripts/check_repository.py
git diff --check
```

Проверяются материалы брендбука, согласованность JSON и TypeScript, содержимое
архива, целостность первичных PDF, структуру конверсий и локальные ссылки документации.
Эти проверки не заменяют визуальную проверку PDF и будущие тесты работающего приложения.
Локальные переходы макета отдельно проверяются через `node scripts/check_prototype.cjs`
при наличии Node.js. Используется имитация DOM; браузерная вёрстка и сервер не проверяются.
Спецификация и примеры API проверяются отдельно через
[check_api_contract.py](scripts/check_api_contract.py); зависимости и команды —
[в пакете контракта](packages/contracts/README.md). Это не проверка работающего сервера.
