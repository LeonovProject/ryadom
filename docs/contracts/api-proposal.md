# Проект API Рядом

Статус: **предложение, маршруты не реализованы, OpenAPI ещё не создан**.
Основание — [требования](../requirements/README.md),
[модель данных](../architecture/data-model.md) и
[права и состояния](../architecture/access-and-states.md).
Пути ниже относительны к предлагаемому префиксу `/api/v1`.

## Контракт и представление данных

- REST, JSON, UUID как строки, даты ISO 8601 с часовым смещением.
- Сессия определяется сервером по cookie; actor ID и роль не принимаются из тела.
- Схемы запросов и ответов предлагается хранить в `packages/contracts` на Zod.
  Сервер проверяет запросы этими схемами; OpenAPI генерируется из тех же схем
  и описаний маршрутов NestJS. Совместимость этого пути проверяется до разделения работ.
- Из OpenAPI генерируется `packages/api-client`; вручную его типы не редактируются.
  ORM-модели в публичные DTO не экспортируются.
- Для списков: `limit` по умолчанию 20, максимум 100; непрозрачный `cursor`;
  ответ `{items, nextCursor}`. Курсор связан с сортировкой и фильтрами.
- Каталог сортируется по `(startsAt, id)` по возрастанию, обсуждение — по
  `(createdAt, id)` по возрастанию; очереди модерации — от старых к новым.
- База использует snake_case, JSON — camelCase. Служебные даты/статусы назначает сервер.
- Неизвестные поля запроса отклоняются, чтобы клиент не мог незаметно передать
  `systemRole`, `reviewedBy` или `publicationStatus`.

OpenAPI и клиент должны строиться воспроизводимо. Изменение схем выполняет
владелец контрактов; UI и сервер получают одну версию. Генерируемый клиент
не заменяет проверки доступа на сервере.

## Сессия и публичный профиль

| Метод и путь | Запрос / результат | Права |
| --- | --- | --- |
| `GET /auth/demo-profiles` | Подготовленные имена, demoKey и обозначения контекстов | Только включённый деморежим |
| `POST /auth/demo-login` | `{demoKey}` → cookie и текущий аккаунт | Только деморежим |
| `POST /auth/demo-register` | `{displayName}` → новый USER, cookie | Только деморежим |
| `POST /auth/logout` | Удаление сессии и cookie, 204 | Повтор также 204 |
| `GET /me` | Аккаунт, доступные организации и возможности | Сессия |
| `GET /accounts/:id` | `{id, displayName}` | Публично |

Предлагаемые пределы: displayName 1–120 символов после trim. Ответ `/me`
не содержит токен сессии. Он помогает отобразить интерфейс, но его кеш не
служит основанием разрешить серверную операцию. POST демовхода при смене профиля
заменяет текущую сессию. Экраны регистрации/входа не обещают проверку пароля.

## Каталог, встречи и свои записи

| Метод и путь | Назначение | Требования / права |
| --- | --- | --- |
| `GET /activity-types` | Направления из списка и созданные пользователями | REQ-SPORT; публично |
| `GET /events` | Каталог: q, city, activityTypeId, joinMode, from, to, organizationId, organizerAccountId | REQ-EVENT; только опубликованные |
| `POST /events` | Создать и сразу опубликовать | S1/S2; сессия, авторство и допуск |
| `GET /events/:id` | Публичная либо ограниченная карточка | REQ-CARD, REQ-UNAVAILABLE |
| `GET /me/events` | Созданные лично; `organizationId` для своих событий организации | Сессия; фильтр организации требует владения |
| `GET /me/participations` | Мои записи со сводками событий; фильтр status, например PENDING,REJECTED | REQ-PARTICIPANTS |
| `GET /events/:id/participations` | Участники и заявки, фильтр по status | Только автор события |
| `POST /events/:id/participations` | Свободная запись или заявка по режиму события | S3/S4; сессия, PUBLISHED |
| `POST /participations/:id/decision` | `{decision: ACCEPT \| REJECT}` | S4; только автор, PENDING, PUBLISHED |

Фильтр `q` предлагается применять к названию/описанию события и названию направления, а `city` — к
регистронезависимому точному совпадению города после нормализации пробелов.
`from` включительно, `to` исключительно; начальное значение from задаёт клиент
для выдачи будущих встреч. Пустой каталог — успешный ответ с пустым items.

`organizerAccountId` фильтрует лично организованные события для публичного профиля
человека; organizationId — события организации. Эти два фильтра взаимоисключающие.
Снятые события не выдаются через публичный каталог ни в одном фильтре.
Привязка маршрутов веба к данным описана в [карте экранов](../product/screens.md).

Пример тела создания, описывающий форму контракта:

```json
{
  "organizer": {"type": "PERSONAL"},
  "activityType": {"name": "Петанк"},
  "title": "Знакомимся с петанком",
  "description": "Покажем правила и сыграем вместе.",
  "startsAt": "2026-11-01T12:00:00Z",
  "timezone": "Asia/Krasnoyarsk",
  "city": "Красноярск",
  "locationText": "У входа в парк, рядом с информационным стендом",
  "conditions": "Можно без опыта. Инвентарь будет на месте.",
  "joinMode": "OPEN"
}
```

Для организации organizer имеет форму
`{type: "ORGANIZATION", organizationId: "<uuid>"}`. Для существующего направления
activityType имеет форму `{id: "<uuid>"}`. Эти варианты взаимоисключающие: нельзя
передать одновременно ID и новое название. Для PERSONAL сервер берёт текущий аккаунт.
Проверка организации и создание нового направления входят в транзакцию создания.

Предлагаемые пределы: title 1–160, description 1–10000, название направления
1–100, city 1–120, locationText 1–1000, conditions 0–4000 символов после trim.
Для нового события startsAt должен быть в будущем по часам сервера; это
предлагаемая политика, а не отдельное требование PDF. ISO-дата и IANA-зона
проверяются раздельно; зона применяется при отображении сохранённого момента.

Обычная карточка содержит описание, направление, organizer с ID, именем и ссылкой
на профиль/страницу, место/время, условия, joinMode, publicationStatus,
confirmedCount, myParticipation (либо null), canJoin и canManageParticipants.
Полные заявки других людей и внутренние данные модерации в неё не входят.
При UNPUBLISHED выдаётся ограниченный DTO согласно
[политике видимости](../architecture/access-and-states.md); различие двух DTO
отражается в схеме ответа, а не угадывается клиентом.

В публичном списке EventSummary содержит id, title, activityType, organizer со
ссылкой, startsAt, timezone, city, locationText, joinMode и publicationStatus.
Для главной достаточно GET /events с limit и from; отдельного API подборок пока нет.
Собственное участие на карточке каталога не обязательно; если его добавляют,
поле персонализируется сервером и не попадает в общий кеш других пользователей.

GET /me/events без organizationId возвращает только личные события текущего
человека, с organizationId — события его организации, включая снятые. Элементы
содержат доступную автору сводку события и canManageParticipants. GET /me/participations
возвращает id/status/decidedAt участия и вложенную сводку event, а не только eventId.
Фильтр status принимает перечень значений PENDING, CONFIRMED, REJECTED через запятую;
фильтрация выполняется сервером до пагинации. Для снятой встречи вложенная сводка
ограничена id, title и publicationStatus; клиент показывает недоступность.
Так вкладки «Участвую / Заявки / Организую» не требуют отдельного запроса на каждую строку.

Ответ участия: id, eventId, accountId, status, decidedAt. Статус OPEN/APPROVAL
не принимается от участника, а читается из события. При первом создании — 201,
при существующей записи — 200 с её текущим состоянием. Отклонённая заявка
повтором запроса не становится новой. После снятия — 409 EVENT_UNAVAILABLE.

## Организации

| Метод и путь | Назначение | Права |
| --- | --- | --- |
| `POST /organizations` | `{name, description, sportInterests}` → частный профиль | Сессия, владелец назначается сервером |
| `GET /me/organizations` | Свои профили, заявки и причины отказов | Сессия |
| `GET /me/organizations/:id` | Частный профиль, заявка, решение, доступные действия | Только владелец; иначе 404 |
| `GET /organizations/:id` | Публичная страница и ссылка на события | Только при APPROVED, иначе 404 |
| `POST /organizations/:id/application` | Подать заявку без служебных полей | Владелец профиля |

Имя 1–160, деятельность 1–4000, спортивные интересы 1–2000 символов — предлагаемые
границы форм. Отдельный юридический статус и загрузка учредительных документов
не требуются. Публичный список событий используется через GET /events с фильтром
organizationId. Неодобренная организация через него не раскрывается.

Подача впервые возвращает 201 и PENDING. Повтор возвращает существующую заявку
с 200; REJECTED не переходит обратно в PENDING. Повторная подача после отказа
не входит в базовое предложение и не показывается как доступное действие.

## Обсуждения и административный контур

| Метод и путь | Назначение | Права / требование |
| --- | --- | --- |
| `GET /events/:id/messages` | Обсуждение с авторами | Опубликовано: публично; снято: только ADMIN |
| `POST /events/:id/messages` | `{body}` → сохранённое сообщение | Сессия, PUBLISHED; участие не требуется |
| `GET /admin/organizations` | Поиск q; approvalState=NOT_SUBMITTED/PENDING/APPROVED/REJECTED | ADMIN; A2 |
| `GET /admin/organizations/:id` | Профиль, заявка, решение, ссылка на события | ADMIN; A2 |
| `POST /admin/applications/:id/decision` | `{decision: APPROVE \| REJECT, reason?}` | ADMIN; S2 |
| `GET /admin/events` | Поиск q, фильтры publicationStatus и organizationId | ADMIN; A2 |
| `GET /admin/events/:id` | Данные/состояние, автор и обсуждение | ADMIN; A2 |
| `POST /admin/events/:id/unpublish` | `{reason}` → результат снятия | ADMIN; S6 |
| `POST /admin/messages/:id/hide` | Скрыть одно сообщение | ADMIN; A3 |

body — обычный текст 1–4000 символов, без исполняемого HTML. Причины — 1–2000
символов после trim. Для REJECT reason обязателен; для APPROVE не передаётся.
Ответ решения включает статус, дату и проверяющего; причина отказа доступна
ответственному организации. Снятие также сохраняет причину для автора события.

NOT_SUBMITTED — вычисляемое отсутствие заявки, не новое значение enum в БД.
Административный поиск охватывает все профили и состояния. GET /admin/organizations/:id
содержит публичную ссылку на ответственного и его имя, application либо null,
а также данные для перехода к GET /admin/events с organizationId.
Детали административного события содержат данные для перехода к человеку/
организации и обсуждению; не дают автоматического права решать заявки участников.

Сообщение в ответе имеет id, eventId, author с публичным именем, createdAt и
status. При HIDDEN body отсутствует у обычного пользователя; ADMIN получает
исходный текст. Связь ответа с организатором определяется сервером по авторству
события. Идентификатор автора сообщения из запроса не принимается.

## Ошибки и повторные действия

Единая предлагаемая форма:

```json
{
  "error": {
    "code": "ORG_NOT_APPROVED",
    "message": "Публикация станет доступна после допуска организации.",
    "requestId": "<request-id>",
    "fieldErrors": {}
  }
}
```

| HTTP | Примеры code | Поведение |
| --- | --- | --- |
| 400 | VALIDATION_ERROR, INVALID_CURSOR | Подсветить поля; сохранить введённое |
| 401 | AUTH_REQUIRED, SESSION_EXPIRED | Запросить вход; не показывать успех операции |
| 403 | FORBIDDEN | Объяснить отсутствие права; права не обходятся сменой URL |
| 404 | NOT_FOUND | Нет ресурса либо он скрыт правилами видимости |
| 409 | ORG_NOT_APPROVED, EVENT_UNAVAILABLE, DECISION_CONFLICT | Обновить данные и показать актуальное состояние |
| 500 | INTERNAL_ERROR | Общий текст и requestId; без внутренних данных БД |

На личном ресурсе можно возвращать 404 вместо раскрытия его существования через
403. Точный порядок: проверка сессии для закрытой операции, поиск и проверка
видимости/права, проверка состояния и выполнение в транзакции.

Повтор одного решения допуска/участия возвращает 200; противоположного — 409.
Повтор REJECT с другой причиной — конфликт, причина не редактируется этим действием.
Повтор снятия с той же причиной возвращает сохранённый результат, с другой —
конфликт. Повтор скрытия возвращает уже скрытое сообщение.
Для решений по участникам снятое событие всегда даёт EVENT_UNAVAILABLE,
даже если пришёл повтор прежнего решения.

Создание события, нового профиля и отправка сообщения пока **не обещают**
идемпотентность при сетевом повторе. Клиент блокирует двойное нажатие и не
повторяет такие POST автоматически. При неопределённом результате предлагает
обновить соответствующий список. Если потребуется автоматический повтор,
контракт дополняется ключом операции, хранением результата и тестами до реализации.

После успешных мутаций клиент обновляет карточку, свои записи, состав или очередь
модерации. Optimistic UI не показывает подтверждённое участие до результата API.
Для автора и второго пользователя нужны повторное чтение/обновление кеша, а не
общий изменяемый объект в браузере, имитирующий сервер.

## Что требуется до превращения проекта в контракт

Назначить владельца, согласовать DTO и ограничения, проверить связку Zod/NestJS/
OpenAPI, создать спецификацию и примеры ошибок, затем генерируемый клиент.
Файлы реализации и спецификация в этой задаче не создавались. Перечень маршрутов
не подтверждает работоспособность приложения.
