## Параллельность и общие файлы

После BASE-01 можно независимо готовить Go-основу, SQL-схему и React-основу.
До OPS-01 проверка этих частей предварительная; готовность основы подтверждает
их общий запуск в Compose. После этого сервер и веб могут работать параллельно
по одному контракту. Веб использует проверяемые фикстуры, пока нужного API нет;
при интеграции заменяет их реальными запросами.

По умолчанию один назначенный владелец ведёт сервер и БД последовательно по
карточкам BE/DB, второй — веб по карточкам FE. Это даёт параллельную работу без
конкурирующих миграций и SQL-генерации. Координатор ведёт контейнеры, общие версии,
контракты и интеграцию пакетов. Единственный BACKEND сам регистрирует модули,
единственный FRONTEND подключает страницы и клиентский кеш. Дополнительный исполнитель проверяет
готовые сценарии; количество агентов само по себе не цель.

Если серверные модули разделяются между агентами, сначала отдельно назначается
владелец каждой SQL-области. Файлы миграций, sqlc-конфигурация и generated/db
остаются у одного владельца. Исполнитель модуля передаёт запрос/потребность в SQL,
а не запускает генерацию поверх чужой работы. Точно так же подключение страниц
в общей навигации выполняет единственный FRONTEND; общие зависимости
по-прежнему меняет COORDINATOR.

## Обязательные точки интеграции

Это обязательные проверки сценариев, а не требование отдельного merge после
каждой строки. Внутри пакета они выполняются по мере готовности, координатор
может принять несколько результатов в конце одной интеграцией.

1. **После основы:** OPS-01 — чистая сборка, готовность API/БД, веб через proxy,
   сохранность данных. DOCS-01 добавляет доступную документацию в тот же образ.
2. **После S1:** BE-04 + FE-05 — создание своего спорта, просмотр другим
   пользователем, сохранение после перезапуска. Сначала устраняются дефекты этого пути.
3. **После S2:** BE-06 + FE-07 — подача, обе ветки допуска, публикация организации
   и публичная страница без повторной модерации события.
4. **После S3/S4:** BE-07 + FE-08/09 — свободная запись, ожидание, принятие/отказ,
   две независимые сессии, защита от дублей. По DEC-14/15 FE-08 также реализует
   личные окна главной и подключает их к BE-07. FE-03 раньше завершает гостевую
   главную/каталог и место подключения; не получает скрытого второго этапа приёмки.
5. **После S5/S6:** BE-08/09 + FE-10/11 — вопрос/ответ, скрытие одного сообщения,
   снятие с причиной и запрет новой записи по прямой ссылке.
6. **После DEC-07:** BE-10 + FE-12 и обновлённые BE-03/04, FE-03/04/05 —
   публикация своего спорта без ожидания, решение/исправление справочника,
   повтор REJECTED, конфликты, поиск и видимость служебных сведений.
7. **После DEC-08:** BE-11 + FE-13 — обе цели жалоб, безопасные повторы/разбор,
   восстановление сообщения, фильтры/версии/права и сохранение после перезапуска.
8. **После DEC-20/21:** AUTH-01/BE-02/FE-02 и BE-13/FE-15 — настоящий повторный
   вход, отзыв двух сессий, сохранение контента и разблокировка до QA-01.
9. **Перед сдачей:** QA-01 и DELIVERY — чистый запуск, мобильный интерфейс,
   сетевой доступ, Swagger/OpenAPI, README, GitVerse и презентация.

Координатор записывает результат каждой точки и возвращает найденный дефект
владельцу отдельной карточкой с шагами воспроизведения. Следующие независимые
задачи могут идти параллельно; сломанный предыдущий путь не считается принятым.

## Размер задачи и срок

Точный срок каждой карточки назначается после первой измеренной задачи;
не выдаём неподтверждённую оценку агенту за гарантию. Ориентир — закончить один
модуль или один экранный путь за запуск, затем проверить и передать результат.
Если назначенный лимит времени исчерпан, задача остаётся незавершённой, с явным
остатком и новым узким поручением. «Почти готово» не закрывает зависимость.

Приоритет — обязательные S1–S6/A1–A6, контейнерный запуск, Swagger и комплект сдачи.
MEDIA-01A/B/C/D/E — выбранные пользователем улучшения после базовой приёмки; их нельзя
молча вычеркнуть. При нехватке времени координатор сообщает конкретный остаток.
Новые идеи не добавляются до воспроизводимой готовности основного объёма.

## Поручение исполнителю

Координатор заполняет пропуски по [шаблону задачи](../task-template.md) и передаёт:

```text
Выполни пакет <ID>: <2–3 карточки в согласованном порядке> из docs/development/tasks/.
Исходный коммит: <SHA с актуальными контрактами>.
Владелец и рабочая копия: <назначение>.
Разрешённые файлы: <список карточки и явно согласованные уточнения>.
Общий контракт: packages/contracts/openapi.yaml, версия 0.13.0.
Внешние зависимости подтверждены: <задачи и свидетельства проверки>.
Внутренние зависимости: <порядок карточек, проверка перед переходом>.
Самостоятельно подключай обработчики/экраны в закреплённых файлах своей стороны.
Не меняй общие схемы/миграции/зависимости вне своей области.
Проверь результат по карточке; реальные команды возьми из текущего README.
Передай изменённые файлы, проверки, результат, ограничения и изменения контрактов.
Не называй мок или частичную реализацию выполненным пользовательским сценарием.
```

Это шаблон будущего поручения, не команда начать работу сейчас. Внутри назначенного
пакета исполнитель продолжает самостоятельно, сохраняя отдельные коммиты/приёмку.
После пакета передаёт результат; следующий пакет назначается отдельно.
