# Swagger UI по адресу прототипа

Дата: 2026-10-19. Статус: **обязательное требование пользователя к результату
разработки**. Это дополнение команды к комплекту сдачи, не требование исходных PDF.
Сейчас Swagger UI и сетевой прототип ещё не развёрнуты.

## Адреса и содержимое

На том же origin, что и приложение, должны быть доступны:

| Путь | Результат |
| --- | --- |
| `/api/docs` | Swagger UI для просмотра API; допустим редирект на `/api/docs/` |
| `/api/docs/` | Страница Swagger UI, доступная по прямой ссылке и после обновления |
| `/api/openapi.yaml` | Текущий OpenAPI-файл, используемый этим Swagger UI |
| `/api/v1` | Базовый путь самого API, как задано в контракте |

Например, если приложение доступно на `https://example.org`, документация
открывается на `https://example.org/api/docs`. Для чтения документации вход
в аккаунт не требуется. Показ схем административных операций не даёт полномочий
на их выполнение; проверки API остаются обязательными.

Документация показывает методы, пути, параметры, схемы запросов и ответов,
HTTP-статусы, ошибки, примеры, требования cookie-сессии и текущую версию контракта.
Источником остаётся [packages/contracts/openapi.yaml](../../packages/contracts/openapi.yaml).
Отдельная вручную поддерживаемая Swagger-спецификация не создаётся.

## Включение в контейнерный процесс

- Координатор контейнерной среды включает Swagger UI в образ `web` вместе с
  его JS/CSS и копией OpenAPI из того же исходного коммита, что API/веб-клиент.
  Версия Swagger UI фиксируется при реализации. Отдельный постоянно работающий
  контейнер для документации не нужен.
- Nginx обслуживает `/api/docs/` и `/api/openapi.yaml` явно, до общего fallback
  React. `/api/v1` по-прежнему проксируется к Go API. Страница приложения вместо
  YAML или Swagger UI не считается работающей документацией.
- Swagger UI загружает спецификацию по `url: /api/openapi.yaml`; её servers.url
  остаётся `/api/v1`. Ресурсы UI поставляются локально, без CDN и сетевого
  обращения к внешнему валидатору (`validatorUrl: null`).
- Поскольку требование — просмотр API, первая версия работает в режиме просмотра
  (`supportedSubmitMethods: []`). Сама загрузка документации не выполняет
  бизнес-операции. Настройки соответствуют [документации Swagger UI](https://swagger.io/docs/open-source-tools/swagger-ui/usage/configuration/).
- При изменении OpenAPI документация пересобирается вместе с приложением.
  Публикуемый YAML должен совпадать с исходным файлом поставляемой версии;
  контейнерный запуск не требует ручного копирования файла на сервер.
- В README и материалах сдачи указываются реальные полные ссылки на Swagger UI
  и OpenAPI после выбора адреса прототипа. Примеры cookie/профилей остаются
  вымышленными; действующие секреты в спецификацию не добавляются.

Способ поставки статических ресурсов описан в
[официальной инструкции Swagger UI](https://swagger.io/docs/open-source-tools/swagger-ui/usage/installation/).
Это требования к будущей реализации, а не подтверждение её готовности.

## Приёмка

- [ ] Из отдельного браузерного контекста без входа `/api/docs` открывает Swagger UI
  на адресе прототипа; переход по прямой ссылке и обновление страницы работают.
- [ ] UI загружает `/api/openapi.yaml` и показывает актуальные операции, модели,
  параметры, ответы, ошибки и примеры без ошибок разбора спецификации.
- [ ] Загруженный YAML совпадает с `packages/contracts/openapi.yaml` поставляемого
  коммита; номер версии соответствует используемому контракту и клиентским типам.
- [ ] JS/CSS и YAML доступны без внешнего CDN/валидатора; обновление контейнеров
  не теряет документацию и не возвращает вместо неё React fallback.
- [ ] Просмотр страницы не вызывает изменяющие запросы API; права защищённых
  операций не зависят от доступности документации.
- [ ] README содержит ссылки по фактическому адресу прототипа.

Эти проверки ещё не выполнены: пока подготовлены только контракт и требования.
