## Декомпозиция основных работ

### Основа и контракты

- Закрепить утверждённые серверные технологии, совместимые версии Go/генераторов,
  конфигурацию TypeScript для веба, `go.mod`/`go.sum` и веб-lock-файл.
- До реализации согласовать карту экранов и схемы блоков ключевых страниц;
  показать успешные, пустые, закрытые и ошибочные состояния, пройти по ним пользовательские пути.
- На первом этапе подготовить Dockerfile, Compose, proxy и пример окружения
  по [обязательному процессу](containerization.md). Контейнеризация не переносится на сдачу.
- Создать SQL-миграции goose, запросы sqlc/pgx, ограничения и явную загрузку демоданных.
- Использовать готовый OpenAPI 0.13.0 и проверенную Go/TypeScript-генерацию;
  при инициализации назначить пути производных и реализовать runtime-валидацию.
  Проверить запрос через контейнерный веб к API и PostgreSQL перед интеграцией модулей.
- Включить Swagger UI `/api/docs` и текущий файл `/api/openapi.yaml` в веб-образ
  по [требованию пользователя](api-documentation.md), проверить через общий proxy.
- Реализовать JWT-сессии, вход email/паролем/регистрацию, текущий аккаунт и очистку кеша при смене.
- DEC-11 уже в BE-02/FE-02: обязательный готовый аватар в форме регистрации,
  общий manifest/listAvatarPresets и атомарное создание аккаунта/аватара/сессии.
  Поздняя MEDIA-01A не блокирует регистрацию; свою загрузку добавляет MEDIA-01D.
- Документировать реальные команды после их появления и проверки в чистой среде.

### Пользовательский контур

- Общие компоненты по брендбуку: кнопки, поля, диалоги, карточки, статусы.
- Каталог с направлениями, простыми фильтрами и состояниями загрузки/ошибки/пустоты.
- Карточка с автором и ссылкой, условиями, временем/местом и понятным режимом записи.
- Создание от человека/своей организации, выбор направления или свой вариант.
- Личные события, собственные записи, состав и отдельный список заявок для автора.
- Вопросы и ответы с различимым авторством, включая вопрос до записи.

### Организации и администрирование

- Частный профиль, подача заявки, ожидание, решение и причина отказа.
- Публичная страница после допуска и публикация без повторного согласования.
- Поиск организаций/событий, сведения/статусы, связанные переходы.
- Одобрение/отказ организации; снятие события с причиной; скрытие одного сообщения.
- Ограниченная карточка снятой встречи для автора/записанных, запрет новых действий.

## Разделение работы между исполнителями

Это будущие области владения; автоматического запуска агентов нет. Применяется
[порядок совместной работы](multi-agent-workflow.md) и [шаблон задачи](task-template.md).

| Область | Будущие пути | Граница ответственности |
| --- | --- | --- |
| Координация и контракты | Корневые файлы, packages/contracts, apps/api/internal/generated/api, packages/api-client, общие конфигурации | Схемы, OpenAPI-генерация, версии, интеграция и документация |
| Контейнерная среда | compose.yaml, infra, Dockerfile, .dockerignore, .env.example | Один владелец сборки, proxy, переменных и проверок; по умолчанию координатор |
| БД | apps/api/db, apps/api/internal/generated/db | Один владелец SQL-миграций goose, запросов/sqlc-генерации и seed-набора |
| API | apps/api/cmd, apps/api/internal/modules, apps/api/internal/transport | Go-обработчики, сервисы, права, транзакции; без смены схемы и производных контрактов |
| Общий UI | apps/web/src/shared/ui, packages/design-tokens | Компоненты, доступность, связь с брендбуком |
| Пользовательский веб | apps/web/src/features/events, participation, discussion | Основной пользовательский путь по утверждённым DTO |
| Организации | apps/web/src/features/organizations | Кабинет, заявка и публичная страница |
| Административный веб | apps/web/src/features/admin | Поиск, решения и модерация |
| Проверка | tests/e2e, интеграционные тесты | Независимое прохождение сценариев и прав |

Если исполнителей мало, зоны объединяются. Если API делится между несколькими
исполнителями, на каждый модуль назначается один владелец. Общие маршруты,
lock-файлы, Go-модуль, SQL-миграции, Compose и клиент не редактируются всеми одновременно.
Моки используют утверждённые DTO и явно обозначаются; интеграция требует реального API.
Каждая интеграция проверяется в Compose; исполнитель передаёт потребность в новых
переменных, зависимостях и миграциях владельцу общей среды.

## Предлагаемый демонстрационный набор

Все данные вымышленные. Воспроизводимые идентификаторы позволяют сценариям
находить нужные данные независимо от порядка карточек.

| Набор | Для чего |
| --- | --- |
| Два обычных аккаунта и администратор | Автор/участник, независимый просмотр, модерация |
| Ответственные организаций | Демонстрация третьей роли и публикации от организации |
| Организация без заявки, PENDING, APPROVED и REJECTED | Все состояния доступа; на отказе есть причина |
| Отдельные заявки организаций для принятия и отказа | Проверка обеих веток без ручного возврата статусов |
| Бег, футбол, шахматы и пользовательское направление | Универсальность и свой вид спорта без правки кода |
| События OPEN и APPROVAL, несколько ожидающих заявок | Свободная запись, принятие и отказ |
| Опубликованное событие с вопросом/ответом и отдельным сообщением для скрытия | Обсуждение и модерация без удаления всей встречи |
| Событие для снятия с подтверждённым участником и PENDING-заявкой | Каталог, прямые ссылки и сохранение старых записей |

Для DEC-07 нужны подготовленные APPROVED и пользовательские PENDING для обеих
веток, REJECTED с причиной и связанные события. Имитации пользовательского ввода
имеют is_seeded=false с создателем, даже если внесены демоскриптом. Проверяются
поиск/новая встреча с REJECTED, исправление свободного имени и конфликт с seed.

Для DEC-08 нужны отдельные жалобы OPEN на встречи и сообщения, закрытые
RESOLVED/DISMISSED, скрытый текст для восстановления и VISIBLE после него.
Версии/даты согласованы; остаются цели для новой жалобы и безопасного повтора.

Даты событий подготавливаются относительно явно выбранной базовой даты демо,
чтобы они оставались будущими; в автоматических тестах часы фиксируются.
Сброс данных — отдельная документированная операция для демонстрационной среды,
по DEC-13 доступен ADMIN в деморежиме через UI/API, а не гостевой маршрут
или побочный эффект обычного старта. Перед защитой нужен
свежий проверенный набор, но эксперт не должен создавать его вручную.

## План проверок

| Уровень | Что проверять | Связь с требованиями |
| --- | --- | --- |
| Схемы и логика | Нормализация направления, переходы, ограничения полей | REQ-SPORT, REQ-JOIN |
| API с PostgreSQL | Связи, UNIQUE, причины, авторство, запрет публикации до допуска | S1/S2/S4, A6 |
| Конкурентные операции | Двойная запись, два решения, запись одновременно со снятием | REQ-PARTICIPANTS, REQ-UNAVAILABLE |
| Изоляция доступа | Чужая организация, чужие заявки, ID из URL, скрытые сообщения | S2/S4/S6, A2/A3 |
| Браузерные сценарии | S1–S6 и A1–A6, включая оба решения по заявкам | Техническая готовность и UX |
| Интерфейс | Телефон/компьютер, клавиатура, фокус, масштаб текста, ошибки | REQ-USABILITY, R6.7 |
| Воспроизводимость | Чистая БД, миграции, seed, перезапуск, сетевой доступ | REQ-DEMO, REQ-DELIVERY |
| Контейнерная среда | Сборка из чистой копии, healthcheck, порядок миграций, постоянный том и proxy | Утверждённые условия команды в ADR-001, поддержка REQ-DEMO/REQ-DELIVERY |

У сценариев должно быть минимум два независимых браузерных контекста: автор и
пользователь; для модерации добавляется администратор. Результаты видны после
повторного чтения и перезапуска, а не только в локальном состоянии React.

Отдельные проверки: UNPUBLISHED блокирует POST по сохранённой ссылке; причина
видна нужному автору; скрытый body не возвращается обычному пользователю;
администратор не решает по чужой заявке участника; при смене демопрофиля не остаётся
кеш предыдущего аккаунта. Конкурентная проверка принимает два законных порядка:
сначала запись, затем снятие — запись сохранена; сначала снятие — записи нет.

Для будущей автоматической проверки нужны форматирование/vet и тесты Go,
проверка TypeScript, генерация OpenAPI/sqlc без расхождений, тесты API/веба и сборка
контейнеров. E2E выполняются перед интеграцией этапа и сдачей через Compose.
Сейчас таких команд, pipeline и тестов приложения нет.

## Дополнительные возможности

По DEC-09/10 MEDIA-01 включает личный SVG-аватар с допуском ADMIN, готовый каталог,
очередь SCR-21 и фон строкой в PostgreSQL с общей серверной проверкой.
MEDIA-00 — общий XML-валидатор, MEDIA-01A — сервер личных аватаров,
MEDIA-01D/E — личный/административный интерфейсы,
MEDIA-01B/C — фон, MEDIA-01F — подключение готовых SVG. По DEC-22
[стартовый аватар и фон](../../design/assets/README.md) уже доступны, ожидания файлов нет.
После DEC-12 до QA-01 нужен хотя бы один реальный готовый SVG. Пустой manifest
блокирует новую регистрацию; вход подготовленными email/паролями остаётся доступен. Общая проверка SVG —
ранняя MEDIA-00, подключение файлов — MEDIA-01F без зависимости от поздней MEDIA-01A/D.
S3 и отдельный
файловый том не используются. [Поля, операции и ограничения](../architecture/media.md)
ещё не реализованы. Первоначальный готовый выбор обязателен для регистрации;
личная загрузка/модерация и фон не блокируют раннюю приёмку основного контура.

Кандидаты EXTRA-01: явный признак «подходит новичкам» с фильтром и экспорт
опубликованной встречи в календарь. Для первого нужны поле, миграция, API и
демоданные; для второго — корректные дата/зона и проверка файла календаря.
Они не считаются утверждённым объёмом. Ни количество функций, ни нативное
приложение сами по себе не обещают дополнительные баллы.

MOBILE-01 остаётся отдельным будущим проектом после веб-приёмки. До него полезно
сохранять API независимым от браузера, но не создавать заранее приложение,
пуш-инфраструктуру и общий пакет веб/native-компонентов без проверки необходимости.
