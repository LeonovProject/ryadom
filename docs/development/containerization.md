# Контейнеризация в процессе разработки

Дата: 2026-10-19. Статус: **обязательное условие команды, утверждено пользователем**.
Основание — [ADR-001](../architecture/backend-decision.md).
Ни Dockerfile, ни Compose-конфигурация пока не созданы. Ниже описан процесс
будущей реализации; готовых команд запуска приложения сейчас нет.

По [DEC-04](../product/decisions.md) сервер уже есть, готовые контейнеры
разворачивает пользователь. Команда проверяет поставку локально и готовит
инструкцию; доступ на сервер и автоматическое развёртывание не требуются.

## Состав среды

| Сервис | Ответственность | Данные и доступ |
| --- | --- | --- |
| `web` | Nginx, React, Swagger UI `/api/docs`, OpenAPI `/api/openapi.yaml`, proxy `/api/v1` и прямые ссылки SPA | Единственная публичная точка входа; HTTPS в демонстрационной среде |
| `api` | Собранное приложение Go, операции и проверки прав | Внутренняя сеть Compose; постоянные бизнес-данные в PostgreSQL |
| `db` | PostgreSQL 17 | Именованный постоянный том; порт не публикуется наружу в демонстрационной среде |
| `migrate` | Одноразовое применение SQL-миграций goose | Запускается после готовности БД и успешно завершается до старта новой версии API |

`migrate` — одноразовая операция, а не четвёртый постоянно работающий сервис.
Seed — отдельная явно вызываемая операция. Обычный запуск не сбрасывает данные,
не загружает seed поверх решений эксперта и не удаляет том.
По DEC-13 ADMIN в деморежиме явно вызывает сброс через аккаунт. Это отдельная
операция: одна транзакция удаления/штатного seed, без удаления тома/схемы или
перезапуска контейнеров. Обычный старт и явное первоначальное наполнение не
получают этого побочного эффекта. Общий seed должен вызываться внутри транзакции.
S3 исключён. Стандартная заглушка входит в образ веба; личные SVG-аватары и фоны хранятся строками в
PostgreSQL; отдельный том для файлов не нужен. См. [решение по медиа](../architecture/media.md).
Готовые SVG входят в веб-образ по общему manifest API/веба. По DEC-22 в нём
есть `ryadom-companion`; исходник подготовлен. Фон из `design/assets/`
передаётся обычной загрузкой или включается проверенной строкой в seed по MEDIA-01B,
а не становится публичной статикой в обход проверки доступа к встрече.

## Первый этап реализации

1. Координатор закрепляет версии Go, PostgreSQL, библиотек, инструментов генерации
   и базовых образов. Go использует свой модуль; веб — отдельный lock-файл.
2. Появляются Dockerfile для API и веба, `.dockerignore`, корневой `compose.yaml`,
   `.env.example` и конфигурация proxy в `infra/`. Это планируемые пути.
3. Многоэтапная сборка API компилирует Go; в runtime попадает исполняемый файл и
   необходимые CA-сертификаты/часовые пояса. API работает от непривилегированного
   пользователя. Веб собирается на стадии Node.js, итоговый образ отдаёт статику.
4. Зависимости, OpenAPI и SQL-генерация доступны внутри закреплённой среды сборки.
   Сборка не использует библиотеки, сгенерированные файлы или артефакты только
   с компьютера разработчика. Версии образов фиксируются, `latest` не используется.
5. PostgreSQL получает healthcheck; миграции ждут готовности БД, API — завершения
   миграций. У API есть проверка жизни процесса и отдельная проверка готовности,
   зависящая от доступности БД. Ошибка подключения даёт неуспешную готовность.
6. На пустой БД выполняются миграции и явная подготовка демоданных. Через `web`
   проверяется первый общий сценарий с двумя пользователями и сохранением данных.
7. Затем документируются фактически проверенные команды сборки, запуска,
   миграций, seed, остановки и диагностики. Пароли/токены задаются окружением;
   в Git попадает только пример без действующих секретов.
8. В тот же веб-образ включаются Swagger UI и исходный OpenAPI текущей версии.
   Маршруты `/api/docs` и `/api/openapi.yaml` не попадают под fallback React;
   [требование и приёмка документации](api-documentation.md) обязательны.

Простой порядок старта контейнеров не означает готовность БД. Compose должен
использовать проверки здоровья и успешное завершение миграций. Основание —
[документация Docker](https://docs.docker.com/compose/how-tos/startup-order/).
Разделение сборки и runtime — [многоэтапные сборки](https://docs.docker.com/build/building/multi-stage/).

## Работа агентов

- Координатор владеет Compose, proxy, Dockerfile, общими переменными и версиями;
  область может быть передана одному явно назначенному исполнителю.
- Владелец БД ведёт миграции и SQL-запросы; запуск генераторов согласует с
  координатором. Два агента не создают конкурирующие изменения одной схемы.
- Исполнитель передаёт новые переменные, системные зависимости, изменения
  миграций и проверку в контейнерах вместе с результатом своей задачи.
- Интеграция проходит на объединённом коде в Compose. Проверки вне контейнеров
  полезны для отладки, но не закрывают контейнерную приёмку.
- Ошибки образов, сети или миграций устраняются на первом этапе. Перенос
  контейнеризации на последние часы перед сдачей не допускается.

## Условия готовности

Это будущие проверки; сейчас ни одна не отмечена выполненной.

- [ ] На чистой рабочей копии образы собираются без установленных на хосте
  `node_modules`, инструментов Go и заранее подготовленных артефактов приложения.
- [ ] После настройки примера окружения документированный путь поднимает веб,
  API и PostgreSQL; миграции завершаются успешно, затем явно загружается демонабор.
- [ ] Веб и API доступны на одном origin; прямой переход на вложенную страницу
  работает; смена демопрофиля и cookie проходят через proxy.
- [ ] `/api/docs` открывает Swagger UI, `/api/openapi.yaml` возвращает контракт
  той же сборки. Документация доступна без входа, локальные JS/CSS загружаются,
  обновление страницы и контейнеров работают; пройдена приёмка api-documentation.md.
- [ ] Созданная встреча, запись, решение и сообщение видны другому пользователю
  и сохраняются после остановки/повторного создания контейнеров с тем же томом.
- [ ] DEC-11: регистрация с готовым ID создаёт аккаунт/аватар/сессию одним commit,
  выбранный avatarUrl приходит сразу. Пропуск/null запрещены, пустой manifest блокирует новую регистрацию;
  вход подготовленными email/паролями остаётся доступен. Ошибочный ID не оставляет частичные записи. Начальный выбор и
  действующая сессия сохраняются после пересоздания контейнеров в пределах её срока.
- [ ] Повторный обычный запуск не меняет пользовательские данные и не создаёт
  дубли демоданных. Повтор применения уже выполненных миграций безопасен.
- [ ] После добавления медиа: SVG-аватар, его модерация/revision и проверенный фон
  сохраняются после пересоздания контейнеров. Публично только APPROVED;
  приватный preview проверяет владельца/ADMIN, старый URL не выдаёт новый файл.
  API и веб собраны с общим avatar-presets.json; готовый `ryadom-companion.svg`
  включён в веб-образ как статика по точному URL manifest. Проверены выбор/сброс/переходы
  PRESET↔CUSTOM, неизвестный/исключённый ID, сохранение source/presetId/revision.
  Proxy не кеширует личные аватары, SVG-фоны и
  ошибки доступа к ним. Снятая публикация проверена по сохранённому URL фона.
- [ ] После добавления загрузки фона: SVG ограничен 131 072 байтами, JSON-тело —
  1 048 576 байтами на proxy и API. Проверены границы лимитов и многобайтный UTF-8;
  превышение даёт 413 без изменения прежнего фона.
- [ ] Недоступная БД даёт неуспешную readiness-проверку; после восстановления
  подтверждается возврат готовности. При ошибке миграций новая версия API не стартует.
- [ ] Все S1–S6/A1–A6 пройдены через контейнерную точку входа, на компьютере
  и телефоне; имитация DOM макета не считается этой проверкой.
- [ ] Принятое DEC-07: состояния/решения/причины направлений и исправленное имя
  переживают пересоздание контейнеров. PENDING/REJECTED не попадают в общий список,
  но используются в событиях; исправление видно второй сессии после чтения.
- [ ] DEC-08: жалобы на обе цели, закрытые решения, версии модерации/жалоб и
  восстановленный текст сохраняются после пересоздания контейнеров с тем же томом.
  Фильтры и независимость прямых/сообщений проверены через реальный API.
- [ ] README описывает реальные команды, демодоступы, переменные, логи, сохранение
  данных и отдельный явный сброс. Сетевое размещение проверено отдельно после
  соответствующего поручения пользователя.

## Передача для самостоятельного развёртывания

Приёмка DEC-13: в отдельной контейнерной БД проверить ADMIN/Origin/подтверждение,
восстановление всех десяти предметных таблиц, новые UUID/даты и удаление сессий.
demo_state/последняя квитанция сохраняются. Ошибка seed откатывает сброс;
параллельные операции проходят общий барьер. Потерянный ответ проверяется по
resetId после нового входа. Затем повторно проверяются основные сценарии и
пересоздание контейнеров. Это не поручение сбросить общую/пользовательскую БД.

В DELIVERY-01A передаются исходники с воспроизводимой сборкой образов, Compose,
пример env без секретов и проверенные команды сборки/запуска/миграций/seed.
Инструкция объясняет настройку внешнего адреса, Origin и HTTPS, постоянный том,
логи, health/readiness и прямое открытие SPA/Swagger/OpenAPI. Приватный registry
не должен быть необходим для сборки. Архитектура сервера и внешний TLS пока
не сообщены; фактические параметры подтверждаются перед передачей.
Сетевая проверка DELIVERY-01B ждёт развёртывания пользователем и реального URL.
Срок сдачи — 20 октября 2026 года в 23:00 по Красноярску (GMT+7), см. DEC-03.

Самостоятельная установка Docker на компьютер пользователя, создание внешнего
хранилища и публикация среды этим документом не выполняются.

## Ключ JWT и реальный вход — DEC-20

API получает AUTH_JWT_SECRET из окружения, base64 >=32 случайных байт; без
корректного ключа не стартует. В .env.example только описание/пустое значение,
в образе/web/логах ключа нет. Обычное пересоздание API сохраняет тот же ключ и
том sessions; сессии продолжаются до exp, если не отозваны. Смена ключа завершает
все текущие JWT и требует нового входа, это описывается в инструкции.
Сетевые email/пароль/JWT идут по HTTPS; точные домен/TLS/Origin задаёт пользователь.
Nginx перезаписывает forwarding-заголовки для ограничений по IP, внешние не
принимаются на доверии. Подготовленные доступы и отсутствие демопереключения —
[спецификация входа](../architecture/authentication.md).
