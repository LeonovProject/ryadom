## Что использовать

DEC-25: [помощник условий](../../product/first-meeting-helper.md),
[печатное приглашение](../../product/printable-invitation.md) и
[четыре карточки передачи](../tasks/first-meeting.md) подготовлены для
отдельного назначения. Новых API/таблиц/маршрутов нет; QR-зависимость и адаптер
имеют владельца COORDINATOR, форма и предпросмотр — FRONTEND, проверка — QA.

- [Сводный manifest](manifest.json): исходный коммит требований, SHA-256 OpenAPI
  и SVG-профиля, владельцы всех 48 карточек и общих файлов. Роли закреплены;
  конкретные агентные задачи пока не запущены.
- [Передача бэкенду](backend.md) и [передача фронтенду](frontend.md): первые
  карточки, актуальные правила и расхождения старого макета.
- [Версии](../../../tools/foundation/versions.json), реальные go.mod/go.sum и
  pnpm-lock.yaml. Генерация транспорта только из packages/contracts/openapi.yaml.
- [SVG-профиль](../../architecture/svg-profile.md) 1.0.0 и его JSON/примеры.
  MEDIA-00 уже реализован и проверен; прикладные SVG-загрузки ещё впереди.

COORDINATOR — текущий интегратор: корневые конфигурации, зависимости, генерация,
контракты, бренд, контейнеры и общая навигация. BACKEND — серверная инфраструктура
и модули; DATABASE — единственный владелец миграций/SQL/sqlc/seed; FRONTEND —
оболочка и features веба; QA — проверка объединённого результата. Если один агент
совмещает BACKEND/DATABASE, карточки и области всё равно остаются отдельными.

Все пути закреплены по наиболее длинному совпадающему префиксу manifest.
Например, apps/api/** принадлежит BACKEND, но go.mod/go.sum и generated
openapi/** — COORDINATOR, db/** и internal/db/** — DATABASE. Веб-зависимости,
Vite-конфигурация и API-клиент общие; прикладной src/** — FRONTEND.

## Проверка основы

Требуются закреплённый Go 1.27.2, Node.js 22.23.1 (также проверяется среда pnpm
на Node 24.19.0), pnpm 11.25.0 и Python 3 с зависимостями контракта. Из корня:

```bash
pnpm install --frozen-lockfile
pnpm generate:api
pnpm check:generated
pnpm typecheck
pnpm build
python3 scripts/check_repository.py
python3 scripts/check_api_contract.py
python3 scripts/check_handoff.py
git diff --check
```

Из apps/api отдельно выполняется `go test ./...`. Без
RYADOM_FOUNDATION_DATABASE_URL проверка живой БД пропускается; это видно в выводе.
Полный независимый запуск с PostgreSQL 17:

```bash
docker compose -f compose.foundation.yaml build
docker compose -f compose.foundation.yaml up -d --wait db
docker compose -f compose.foundation.yaml run --rm go-check
docker compose -f compose.foundation.yaml run --rm web-check
docker compose -f compose.foundation.yaml down
```

Это отдельный проект ryadom-foundation: без открытых портов, с временной БД,
без предметных таблиц и без обращения к существующим сервисам. Контрольный пароль
используется только в этой изолированной проверке, не в продуктовой поставке.
Новая продуктовая compose.yaml/постоянный том/миграции/секреты — задача OPS-01,
а не готовая возможность compose.foundation.yaml. Веб пока показывает только
проверочную страницу сборки; регистрации/встреч/авторизации здесь нет.

## История первоначальных назначений BASE-01

1. Проверить чистоту рабочей копии и SHA итогового коммита; выполнить проверки.
2. От этого SHA назначить отдельно BE-01, DB-01 и FE-01 в ветках
   `codex/be-01-foundation`, `codex/db-01-schema`, `codex/fe-01-shell`.
   Ветки/worktree создаются при назначении, не являются уже запущенной работой.
   Владельцев общих файлов не менять внутри предметной карточки.
3. COORDINATOR подключает результаты в OPS-01 и DOCS-01: рабочий контейнерный
   HTTP-маршрут с БД, readiness схемы, постоянный том, локальный Swagger UI.
   Подготовительная проверка SELECT 1 не закрывает эту точку интеграции.
4. Далее AUTH-01/DB-02/BE-02, MEDIA-00/01F и соответствующие FE-карточки.
   Первый продуктовый путь: регистрация с явным аватаром → создание встречи →
   просмотр другим пользователем. Проверять через реальные операции в Compose.
5. Затем остальные карточки без сокращения DEC-17; ранняя QA-01 и окончательная
   DELIVERY-01A после всех MEDIA. Сетевая DELIVERY-01B — после развёртывания
   пользователем, с фактическими URL/TLS/Origin и материалами GitVerse.

В назначении указывать одну карточку, точный SHA, владельца, разрешённые файлы,
зависимости, проверки и наблюдаемый результат. Не выдавать всю роль одним заданием.
Коммит подготовки не разрешает автоматический push, запуск других чатов или
развёртывание на сервере пользователя.
