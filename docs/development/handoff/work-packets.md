# Работа пакетами

Принято пользователем 20 октября после интеграции BE-03 (`b43dab2`). Этот порядок
заменяет обязательную остановку после каждой карточки и передачу координатору
обычного подключения маршрутов. Продуктовый объём и API 0.13.0 сохраняются.

## Правила выполнения

1. Назначение содержит 2–3 связанные карточки, порядок, одного исполнителя,
   исходный SHA и объединённую область файлов. При необходимости допустима одна
   самостоятельная карточка. Весь backlog одним пакетом не назначается.
2. Исполнитель работает в одной ветке/worktree и делает отдельные коммиты по
   карточкам. После проверенной карточки переходит к следующей **в назначенном
   пакете** без нового согласования и без промежуточного merge в main.
3. Внутреннюю зависимость подтверждает проверка результата в этой же ветке.
   Ждать её появления в main не нужно. Внешняя зависимость должна быть доступна
   в исходной базе или согласованном снимке; наличие одного DTO не закрывает её.
4. В конце передаётся один результат пакета: SHA, состояние каждой карточки,
   проверки с привязкой к проверенному SHA, снимки/логи при необходимости,
   ограничения и остаток. Код без подключения не считается готовым модулем.
5. Координатор читает diff и отчёт, принимает подтверждённые проверки исполнителя
   и проверяет подключение/изменившиеся места общей сборки. Полный набор тестов
   повторяется при конфликте, изменении кода, несовпадении проверенного SHA,
   сбое или конкретном незакрытом риске. Обязательные QA/DELIVERY сохраняются.
6. Проверки S1–S6 выполняются внутри пакета по мере готовности; их можно передать
   одним отчётом в конце. Меньше слияний не означает пропуск сценариев или
   объявление фикстур реальной интеграцией.

## Подготовленные пакеты

BE-P1/FE-P1 уже [объединены и приняты локально](../integration/2026-10-20/p1/README.md).
Следующие BE-P2/FE-P2 готовы к назначению по зависимостям; незакоммиченная BE-07
не считается частью принятого результата. Работы этим документом не запускаются.

| ID | Порядок карточек | Результат и внешние зависимости |
| --- | --- | --- |
| BE-P1 | BE-04 → BE-05 → BE-06 | Публикация встречи, организации и допуск. BE-03/BE-02 готовы; общий проход S1/S2 в конце |
| BE-P2 | BE-07 → BE-08 → BE-09 | Запись/решения, обсуждение и модерация встреч. После проверенного BE-P1; S3–S6/A2/A3 |
| FE-P1 | FE-03 → FE-04 → FE-05 | Принят локально вместе с BE-P1; публичная организация/создание прошли реальный S1/S2 |
| FE-P2 | FE-08 → FE-09 → FE-10 | Запись/мои встречи/личная главная, состав/решения, обсуждение. Клиентская основа готова; реальные S3–S5 ждут BE-07/08 из BE-P2 |

Это подготовленные назначения, а не запуск/перезапуск агентов. Уже начатую
BE-04 и коммиты FE-03 сохранить, не писать заново и не делать reset. До
передачи нового назначения работающий агент не обязан узнать об изменении
инструкций автоматически. Результаты BE-P1 и FE-P1 можно объединить одной
точкой после их совместного прохода. Если фронтенд раньше упирается в BE-04,
допустима ранняя передача проверенного серверного коммита.

Остальные пакеты назначаются отдельно по зависимостям. Карточки/статусы остаются
единицей учёта: 48 прежних карточек не заменяются крупными задачами.
Подготовленные пакеты и их области — в [manifest](manifest.json).

## Владельцы подключений

- Один BACKEND/DATABASE ведёт сервер и SQL последовательно. Он самостоятельно
  регистрирует модули в `apps/api/cmd/api/main.go`, добавляет относящиеся SQL и
  запускает sqlc. Схема/миграции меняются только при отдельном назначении DATABASE.
- Один FRONTEND подключает экраны в `App.tsx`, `routes.ts`, `AppShell.tsx` и
  обновляет общие ключи клиентского кеша в рамках своего пакета. Действующий
  вход/демодоступы и согласованные права сохраняются. QR-адаптер остаётся общим.
- COORDINATOR сохраняет OpenAPI/общий клиент и генерацию Go/TS, зависимости и
  lock-файлы, контейнерную конфигурацию, бренд, корневые документы/очередь.
  Координатор не редактирует подключение API или веба одновременно с владельцем
  пакета; нужную правку сначала передаёт ему либо согласует передачу файла.
- Дополнительный агент внутри одной стороны получает непересекающийся scope;
  `main.go`, общая веб-навигация и SQL-генерация всё равно имеют одного владельца.

## Когда нужна ранняя передача

- Проверенный результат разблокирует другую сторону, у которой закончилась
  независимая работа. Можно передать конкретный SHA/снимок для локальной проверки;
  merge в main нужен только когда это действительно решает блокировку.
- Меняется общий контракт, зависимость, схема/миграция или пересекаются файлы
  владельцев. Сначала согласовать изменение, продолжая независимую часть.
- Обнаружена поломка уже принятого пути, препятствующая продолжению.

Обычная регистрация endpoint, завершение одной карточки и сообщение «код готов»
сами по себе не требуют координаторской интеграции. В конце пакета остановиться
и передать результат; следующий пакет самовольно не начинать. Правила push,
развёртывания и сообщений в другие чаты этим решением не расширяются.
