# Блокировка аккаунта — DEC-21

Статус: **принято для MVP, не реализовано**, 2026-10-19. Пользователь выбрал
сохранение контента: ADMIN снимает встречи и скрывает сообщения отдельно.
Это улучшение сверх обязательного минимума PDF (A-P07). Вход —
[DEC-20](../architecture/authentication.md), транспорт — [API 0.13.0](../contracts/api-v1.md).

## Доступ и последствия

ADMIN блокирует и разблокирует USER до ручного обратного решения. Нет таймера,
поля причины и жалобы непосредственно на аккаунт. ADMIN не может быть целью:
409 ACCOUNT_PROTECTED, включая самого себя. Смена роли этим действием запрещена.

ACTIVE → BLOCKED завершает все сессии во всех браузерах/устройствах одним commit.
Вход и любые действия с авторизацией запрещены, включая создание/управление
встречами, разбор заявок, обсуждение, жалобы, загрузку SVG и действия от имени
своих организаций. Прямой API-запрос проверяет то же правило. Публичный просмотр
как гостю сохраняется; блокировка аккаунта не блокирует устройство или человека.

При BLOCKED → ACTIVE разрешён новый вход. Старые JWT остаются отозванными.
Нет фонового восстановления сессий и автоматического входа. Уже отправленный
запрос либо завершился до commit блокировки, либо отклонён после ожидания;
порядок замков — [в спецификации входа](../architecture/authentication.md).

Публикации, обсуждение, направления, аватары и участия остаются в прежнем
состоянии. Организация сохраняет допуск и публичную страницу, но единственный
ответственный не может ей управлять. ADMIN не получает полномочий принимать
заявки участников вместо автора. На опубликованные встречи по-прежнему можно
записываться до начала, включая заявки, которые заблокированный автор пока
не сможет разобрать. Интерфейс предупреждает об этом до отправки заявки.
В свободном режиме подтверждение работает по обычным правилам.

Текущая блокировка видна публичным признаком PublicAccount.isBlocked;
OrganizationOrganizer/PublicOrganization.ownerIsBlocked отражает ответственного.
Причина/дата/ADMIN/email не раскрываются. В профиле и возле автора —
«Аккаунт заблокирован»; во встрече/организации — «Организатор временно недоступен».
Это не подписи отмены, снятия или отказа. Участники и другие пользователи могут
писать в сохранённом обсуждении. Уже подтверждённое участие заблокированного
пользователя сохраняется, новой записи или действий от него нет.

Жалобы на контент не закрываются автоматически. ADMIN может отдельно снять
встречу с обязательной причиной, скрыть/восстановить сообщение или модерировать
аватар. Жалоба не блокирует автора сама. Отзыв допуска организации, передача
владения и автоматическое снятие всех публикаций не добавляются.

## Экран ADMIN и API

SCR-22 `/admin/accounts`: поиск по имени/email/точному ID, фильтр ACTIVE/BLOCKED,
пагинация; показ роли и текущего состояния. Выбранный аккаунт открывается в панели
того же маршрута, отдельная страница не требуется. ADMIN виден без доступной
кнопки блокировки. Для USER — подтверждение с именем и последствиями, затем
блокировка либо разблокировка. Поле причины отсутствует.

| Операция | Назначение |
| --- | --- |
| adminListAccounts | GET /admin/accounts: q/status, createdAt/id DESC; фильтры до LIMIT, курсор связан с ними |
| adminGetAccount | GET /admin/accounts/{accountId}: приватный AdminAccount для панели и перечитывания |
| adminSetAccountStatus | PATCH /admin/accounts/{accountId}/status: status + expectedRevision; ответ AdminAccount |

AdminAccount содержит вложенный PublicAccount, приватный email, systemRole,
status, revision, blockedAt, blockedByAccountId, createdAt. ACTIVE: обе blocked-поля
null; BLOCKED: обе заполнены. Изменение статуса увеличивает revision с 1 на единицу.
При той же revision и том же статусе 200 без изменения; устаревшая revision
всегда 409 ACCOUNT_REVISION_CONFLICT. Старое решение не отменяет новое.

Во время запроса кнопки отключены, успех только после подтверждённого ответа.
После конфликта/таймаута перечитать adminGetAccount. Нет автоматического PATCH
retry; свежие данные показывают состояние, но не доказывают авторство потерянного
запроса. При ошибке сохраняются прежние данные, доступен явный повтор после чтения.

## Работа и приёмка

BE-02 заранее реализует проверку ACTIVE и JWT-сессий для всех защищённых модулей.
BE-13 добавляет административные операции в аккаунты после BE-02, FE-15 — SCR-22
после FE-11; общие маршруты/навигацию подключает координатор. У BE-13 нет
параллельного владения auth/accounts с ещё незавершённой BE-02.

- Две сессии USER → блокировка → обе теряют доступ, прямой запрос отклонён.
- Неверный пароль BLOCKED даёт общую ошибку входа; правильный — ACCOUNT_BLOCKED.
- Обычный USER/гость не блокирует других; любой ADMIN защищён от блокировки.
- Разблокировка разрешает новый вход, но не возвращает старые JWT.
- Встречи, обе формы участия, сообщения, допуск и открытые жалобы сохраняются;
  недоступность организатора обозначена и не выдаётся за снятие публикации.
- Проверены конкурентные действия, старые revision, потерянный ответ,
  сохранение после рестарта и сброс к сиду в отдельной тестовой БД.

Это критерии будущей проверки, не отчёт о работающей функции.
