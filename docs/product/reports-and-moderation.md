# Жалобы и восстановление сообщений — DEC-08

Статус: **принято для MVP; реализация не начата**. Пользователь выбрал жалобы
на встречи и сообщения, без ввода причины, с ручным решением администратора
и восстановлением скрытого сообщения. Это улучшение команды сверх первичных PDF.
Обязательная причина снятия встречи и отказа организации сохраняется.
Транспорт — [OpenAPI 0.13.0](../../packages/contracts/openapi.yaml), хранение —
[модель данных](../architecture/data-model.md), задачи —
[BE-11/FE-13](../development/tasks/reports.md).

## Кто и на что жалуется

- Вошедший пользователь может пожаловаться на опубликованную встречу или на
  видимое сообщение её обсуждения. Запись на встречу не требуется; время начала
  не закрывает жалобы. Оба режима участия имеют одинаковые правила.
- Гость получает предложение войти. ADMIN может подать жалобу как пользователь,
  но для модерации ему доступны отдельные административные действия.
- На свою встречу, включая встречу своей организации, и на собственное сообщение
  жаловаться нельзя. Автор встречи может пожаловаться на чужое сообщение;
  организатор от этого не получает права скрывать его.
- «Пожаловаться» — одна кнопка, без категории, текста, вложений и поля причины.
  До подтверждённого ответа сервера интерфейс не показывает успех.
- Одна жалоба одного аккаунта на одну цель за всё время. Повтор возвращает
  существующую квитанцию, включая уже рассмотренную. Отмена жалобы и повторное
  открытие закрытой жалобы в MVP не предусмотрены.

Порядок проверки: сессия/Origin → доступ к встрече и публикация → собственный
контент → существующая жалоба → доступность новой цели → создание. Снятая
встреча даёт 409 EVENT_UNAVAILABLE автору/участнику/ADMIN, постороннему — 404.
Новая жалоба на HIDDEN запрещена; повтор уже существующей возвращает её текущий
статус, если сама встреча ещё опубликована. Ни название цели, ни скрытый текст
не возвращаются в квитанции. В ней только id, target, status, createdAt, reviewedAt.

Клиент показывает «Жалоба отправлена» для OPEN и «Жалоба уже рассмотрена» для
RESOLVED/DISMISSED. Может помнить квитанцию в кеше текущего аккаунта; при смене
аккаунта кеш очищается. После перезагрузки повтор безопасно получает ту же запись.
Отдельной истории жалоб и рассылки о решении в MVP нет.

## Разбор администратором

Отдельная страница не нужна. В SCR-17 остаются поиск и фильтры публикации,
организации/направления; добавляются «Есть жалобы» и два счётчика:
OPEN на встречу и OPEN на сообщения. Снятые встречи тоже можно найти.
Фильтр учитывает обе группы: жалобы на сообщения не теряются после снятия встречи.

В SCR-18 администратор видит исходные сообщения, статус, OPEN-счётчик и может
фильтровать обсуждение по наличию жалоб. Личности заявителей, категории и свободные
тексты для ручного разбора не требуются. Публичные DTO не получают счётчиков,
служебных версий, дат/авторов модерации или данных заявителей.

| Действие ADMIN | Контент | OPEN-жалобы |
| --- | --- | --- |
| Скрыть сообщение | Только это сообщение становится HIDDEN | Только его жалобы → RESOLVED |
| Восстановить сообщение | Оно становится VISIBLE на прежнем месте | Закрытые остаются закрытыми |
| Снять встречу с причиной | Встреча UNPUBLISHED, обычное обсуждение недоступно | Прямые жалобы на встречу → RESOLVED; жалобы на сообщения остаются OPEN |
| Отклонить жалобы на встречу | Публикация не меняется | Только прямые OPEN → DISMISSED |
| Отклонить жалобы на сообщение | Видимость не меняется | Только его OPEN → DISMISSED |

У закрытых жалоб сохраняются reviewedAt и reviewedBy; повтор не переписывает
решение. Жалобы никогда не скрывают контент автоматически — даже при большом
счётчике. Скрытие и снятие разрешены и без жалоб. Массового скрытия обсуждения нет.
Если при повторном запросе цель уже в нужном состоянии, операция возвращает
текущее состояние без нового перехода и без переписывания дат.

## Восстановление и одновременная работа

Восстанавливает только ADMIN, без причины. ID, текст, автор, createdAt и порядок
сообщения сохраняются. Публичное чтение снова возвращает body для VISIBLE.
HIDDEN по-прежнему возвращает заглушку без body даже самому автору и ADMIN
на публичном маршруте. AdminMessage содержит оригинал в любом состоянии.

Восстановление возможно и внутри UNPUBLISHED, но не возвращает встречу в каталог
и не открывает обсуждение обычным читателям. Восстановление публикации встречи,
редактирование/удаление своих сообщений и блокировки аккаунтов отложены.

Чтобы запоздавший запрос не отменил более новое решение, AdminMessage содержит
moderationRevision. Для скрытия и восстановления обязателен expectedRevision:

1. Под блокировкой event → message сервер проверяет текущее состояние.
2. Если оно уже нужное, возвращает 200 без изменений, даже с прежней версией.
3. Иначе версии должны совпадать; устаревшая даёт 409 MESSAGE_CHANGED.
4. При переходе moderationRevision увеличивается на один. hiddenAt/By сохраняют
   последнее скрытие, restoredAt/By — последнее восстановление; обратный переход
   не стирает предыдущую пару. Текущий статус задаётся status, не сравнением дат.

Пример: hide(expectedRevision=0) → HIDDEN, revision=1; restore(1) → VISIBLE,
revision=2. Повтор старого hide(0) получает конфликт и не скрывает текст заново.

Для отклонения жалоб действует отдельная версия: eventReportsRevision у встречи
(только прямые жалобы) и reportsRevision у сообщения. Новая уникальная жалоба
увеличивает соответствующую версию; закрытие непустой группы OPEN — тоже на один.
Повтор жалобы/решения без изменений версию не увеличивает. Счётчики вычисляются
по OPEN, отдельно от версии и от статусов публикации/сообщения.

Отклонение принимает expectedReportsRevision. Если OPEN нет, это безопасный
повтор 200; иначе несовпадение даёт 409 REPORTS_CHANGED. Так старый повтор
не закрывает новые жалобы, появившиеся после первого решения. Закрытие при
скрытии/снятии атомарно с переходом самого контента и не требует второй формы.

При конфликте или неизвестном результате клиент перечитывает adminGetEvent либо
adminGetMessage и показывает актуальное состояние. Последний доступен напрямую,
даже если строка исчезла из фильтра «Есть жалобы». Старый запрос не отправляется
заново с автоматически подставленной новой версией; новое решение требует действия
администратора. Текст после отклонения: «Жалобы рассмотрены», без обещания, что
контент опубликован: другой администратор мог изменить его состояние.

## Будущая проверка

- Жалоба без записи на встречу, оба режима, до/после начала; гостевой вход и
  запрет собственных целей. Ошибка/таймаут не дают ложного успеха.
- Два параллельных запроса одного аккаунта создают одну запись и возвращают
  один id. Разные аккаунты увеличивают счётчик независимо.
- OPEN/RESOLVED/DISMISSED независимы от публикации, допуска организации и участия.
- Скрытие одного текста закрывает только его жалобы; снятие встречи — только
  прямые. Остальные жалобы доступны администратору через фильтры снятых событий.
- Скрыть → восстановить → снова скрыть; безопасные повторы, старые запросы,
  одновременные решения, новая жалоба во время разбора. Нет утечки оригинала HIDDEN.
- Сохранение после пересоздания контейнеров с тем же томом PostgreSQL, в том числе
  версий, дат и закрытых жалоб. Проверки выполняются на реальном API/БД после реализации.

Статические примеры контракта описывают ожидаемые ответы. Они не доказывают
работу транзакций, прав, интерфейса или контейнерного хранения.
