# Проверка согласованности перед разработкой

Дата актуализации: 2026-10-20. Текущее дополнение — DEC-22/23, API 0.13.0, 44 карточки,
21 URL. Предыдущие проходы ниже относятся к API 0.11/0.12 и прежним 41 карточке. Приложения/БД/контейнеры ещё не реализованы.
Проверка документации не подтверждает работоспособность будущей платформы.
Первичные [постановка и критерии](../requirements/README.md) сохраняют приоритет;
выбранные улучшения команды перечислены отдельно в [решениях](decisions.md).

## Вопросы, решённые пользователем в ходе проверки

1. **Полный личный список — DEC-15.** «Участвую» по умолчанию показывает
   предстоящие по началу ASC. «Начавшиеся» — все начатые по началу/ID DESC,
   без вывода о посещении/окончании. Видимая ссылка «Все записи» сохраняет
   ограниченные снятые публикации. Во вкладках заявок/авторства порядок прежний.
2. **Переход после входа/регистрации — DEC-16.** Допустимый безопасный returnTo,
   иначе персональная главная `/`. Прежние default `/events` и `/me` заменены.
   Автоматические бизнес-действия после входа не добавлены.
3. **Объём к сроку — DEC-17.** Весь ранее согласованный объём сохраняется,
   личные SVG/фоны не переносятся. Неподтверждённые идеи EXTRA-01/React Native
   не включены этим выбором. Срок — 20 октября 2026, 23:00 GMT+7.

На первом проходе API 0.11.0 добавил STARTED существующему eventWindow; новый маршрут,
таблица или схема DTO не нужны. Порядок должен применяться на сервере до LIMIT.
Это не сортировка загруженной страницы в браузере.

Это не требует повторного выбора Go/PostgreSQL, лимита SVG, модерации,
часовых поясов или срока сдачи. Карты, вместимость, уведомления, отмена записи,
нативное приложение остаётся вне принятого объёма. DEC-20 позднее добавил настоящий вход.

Прежнее ограничение повторного входа нового демопрофиля снято DEC-20:
теперь принят email/пароль с JWT, без восстановления пароля/подтверждения почты.
[Аутентификация](../architecture/authentication.md) и
[блокировка](account-blocking.md) заменяют прежние правила, реализации ещё нет.

## Проверки и пределы результата

- В таблице и карточках 41 уникальный ID, зависимости совпадают, формальных
  циклов нет. Все 58 operationId упомянуты в карточках; это не доказательство
  реализации. Скрытая зависимость приёмки MEDIA-01F исправлена отдельно.
- Схемы OpenAPI/HTTP-примеры, генерация Go/TypeScript и проверки репозитория
  выполняются по [пакету](../../packages/contracts/README.md) и
  [отчёту](../contracts/validation.md). Они не исполняют сервер, SQL или UI.
- Макет 0.2 не обновлялся после остановки пользователем. Его прежние переходы,
  порядок и 18 маршрутов не являются реализацией API 0.12.0 или полной карты
  20 маршрутов. Новая визуальная проверка этим разбором не выполнена.
- На момент первого прохода код приложения, миграции, контейнеры и изображения
  не были созданы; позднее DEC-22 добавил стартовые SVG. Коммит/push этой работы
  не выполнялись. Оставшиеся проверки функциональности относятся к будущей
  разработке и локальной/сетевой приёмке.

## Второй проход: контракты, границы модулей и время

Пользователь поручил продолжить проверку. Исправления не запускают разработку
приложения и не сокращают согласованный объём DEC-17.

| Найдено | Исправлено / зафиксировано |
| --- | --- |
| В listMessagesSuccess и adminListMessagesSuccess две разные строки VISIBLE/HIDDEN имели один ID | Сообщения получили разные ID в JSON и OpenAPI. Валидатор теперь отклоняет дубли ID, в том числе у вложенных event/participation, и расхождение одноимённых примеров |
| API отдавал первую страницу старейших сообщений, но интерфейс должен показывать свежий вопрос/ответ | Пользователь принял DEC-18: явный NEWEST_FIRST и курсор к ранним, хронология загруженного диапазона ASC в UI. После обновления новый хвост не склеивается со старыми страницами через пропуск |
| Каталог обещал фильтр даты, API имел только абсолютные from/to, а зона календарного дня не была определена | По выбору пользователя DEC-19 введены dateFrom/dateTo по локальной дате каждой встречи, границы [from,to), AND с абсолютными моментами до LIMIT |
| Общее правило reason при REJECT стояло рядом с решением по участию | Явно разделены отказ участнику без причины и отказ организации/направлению с причиной; восстановление сообщения/аватара отделено от отсутствующего восстановления публикации |
| Перечитывание списка после потерянного ответа можно было ошибочно трактовать как доказательство успеха по совпавшему тексту/названию | Уточнено, что поля не уникальны и не являются квитанцией запроса. Результат остаётся неподтверждённым, автоматического повторения POST нет |
| Фильтр hasOpenReports в ранних административных операциях относился текстом к поздней BE-11, хотя жалобы уже есть в DB-02 | Полные фильтры/счётчики закреплены за BE-08/09 до пагинации. BE-11 переиспользует готовые чтения/закрытие, добавляет подачу/разбор/восстановление |
| Общий барьер транзакции требовал проверки авторизации, но не различал в описании public и optional-session | Оболочка BE-01 проверяет режим конкретного маршрута: публичный не требует cookie, optional допускает отсутствие, закрытый проверяет права. Барьер сброса сам по себе не закрывает публичное чтение |
| Крупная очередь всё ещё предлагала повторно согласовать принятые правила и не отражала все обязательные зависимости ранней QA/полной поставки | PLAN-01 не переоткрывает DEC/API; QA-01 учитывает ранние улучшения/готовые файлы, DELIVERY-01 ждёт весь MEDIA и финальную локальную проверку |
| Для времени были подробнее описаны показ UTC и право записи, чем ввод в другой зоне и устаревание личных окон | FE-05 преобразует ввод по зоне встречи, не устройства; FE-08 обновляет оба окна на границе начала/местного дня с новым referenceTime, без старых курсоров |

Новые решения DEC-18/19 отражены в [контракте](../contracts/api-v1.md),

Повторены проверка OpenAPI/примеров, генерация и компиляция Go/TypeScript,

## Дополнение DEC-20/21 — вход и блокировка

API 0.13.0: 60 операций, 100 схем, 280 HTTP-примеров, 64 отрицательные формы.
Демовыбор исключён, register требует email/password/displayName/presetId,
повторный вход работает по проекту. JWT проверяется с sessions/ACTIVE в БД.
Блокировка USER завершает все сессии, контент/допуск/участия сохранены;
ADMIN нельзя блокировать. Защита от гонки задана общим порядком замков.

AUTH-01 отделяет криптографию/ограничения от BE-02; BE-13/FE-15 добавляют
административный путь SCR-22 до QA-01. Всего 44 карточки/21 URL/11 таблиц.
По последующему DEC-22 SVG уже подготовлены, ожидание файлов снято.
Параметры сетевого сервера остаются внешней зависимостью.
Статические схемы/примеры не исполняют JWT, Argon2id, SQL или интерфейс.
