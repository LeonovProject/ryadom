# Принятые уточнения перед разработкой

Дата: 2026-10-19. Статус: **принято пользователем в ответах на вопросы**.
Это решения команды в пределах [постановки](../requirements/assignment.md),
а не новые критерии официальных PDF. Исторические записи описывают состояние
на дату решения; текущая реализация — в CONTEXT.md и отчёте интеграции.
Транспортные изменения закреплены в [API 0.13.0](../contracts/api-v1.md).

## DEC-01 — Закрытие записи в момент начала

Новая запись и принятие/отклонение ожидающих заявок доступны только до начала
встречи. Граница включительна: при серверном `now >= startsAt` они закрыты
для обоих режимов — OPEN и APPROVAL.

Конкретизация для согласованной реализации:

- API проверяет время после блокировок, непосредственно перед операцией.
  Время устройства и время поступления HTTP-запроса не разрешают запись.
  Ожидание блокировки не должно сохранять устаревшее время начала транзакции.
  Операция, прошедшая окончательную проверку до границы, может завершить commit
  после неё; завершившийся до границы запрос не отменяется задним числом.
- После обычных проверок доступа сначала проверяется снятая публикация
  (`409 EVENT_UNAVAILABLE`), затем начало (`409 EVENT_STARTED`). Эти проверки
  предшествуют возврату повтора joinEvent/decideParticipation. После начала
  сохранённый результат восстанавливают чтением, не повтором изменяющего запроса.
- Начало не меняет PUBLISHED на UNPUBLISHED и не создаёт новый статус публикации.
  Карточка и обсуждение опубликованной встречи остаются доступны по прежним правам.
  Просмотр состава автором, модерация и смена фона сохраняют прежние правила.
- CONFIRMED/REJECTED сохраняются. Не рассмотренная до начала заявка остаётся
  PENDING; автоматического отказа и подтверждения нет. Интерфейс поясняет:
  «Заявка не рассмотрена до начала встречи», не обещая дальнейшего решения.
- `canManageParticipants` разрешает чтение состава автором.
  Новое `capabilities.canDecideParticipations` отдельно разрешает решения до
  начала. После начала `canJoin=false`, `joinBlockedReason=EVENT_STARTED`,
  `canDecideParticipations=false`. Причина начала имеет приоритет перед
  AUTH_REQUIRED/ALREADY_ORGANIZER/ALREADY_PARTICIPATING в опубликованной карточке.
- Открытая страница обновляет состояние на границе времени и после возврата
  к вкладке. Клиентский таймер служит удобству; окончательное решение принимает API.
  После EVENT_STARTED клиент перечитывает карточку/участие и сохраняет введённый
  текст сообщения. Кнопки вопроса и чтение обсуждения из-за начала не исчезают.

Время окончания не вводится. Прошедшее время начала не доказывает, что встреча
завершилась или человек посетил её. Главная/каталог будущих встреч передают `from`;
собственные списки и прямая ссылка могут показывать уже начавшуюся встречу.

| Будущая проверка с управляемыми часами | Результат |
| --- | --- |
| `now = startsAt - 1 мс` | Действуют обычные правила OPEN/APPROVAL и решения автора |
| `now = startsAt` и `now = startsAt + 1 мс` | Обе операции дают 409 EVENT_STARTED без изменения участия |
| Запрос пришёл раньше, блокировку получил после начала | Запись/решение отклонены по актуальному времени |
| Повтор записи или прежнего решения после начала | 409 EVENT_STARTED; сохранённый результат доступен чтением |
| Автор читает состав после начала | Состав доступен, решения недоступны |
| PENDING и обсуждение после начала | PENDING сохранён, вопрос/ответ доступны для опубликованной встречи |
| Снятая и уже начавшаяся встреча | Сначала применяются видимость и правила снятой публикации |

Затрагивает BE-03/07, FE-04/08/09 и QA-01 из [очереди задач](../development/tasks/README.md).
Примеры HTTP описывают ожидаемые ответы; проверки сервера/БД ещё не выполнены.

## DEC-02 — Время встречи в её часовом поясе

В карточках каталога, на странице встречи, в своих списках, управлении,
административных списках и сводке перед публикацией дата/время начала отображаются
по IANA-зоне самой встречи. Рядом всегда есть явное смещение GMT/UTC для этой даты;
в деталях можно дополнительно показать название зоны. Зона устройства не меняет
показываемое время встречи автоматически.

Пример: `startsAt=2026-11-07T05:00:00Z`, `timezone=Asia/Krasnoyarsk` →
«7 ноября, 12:00 (GMT+7)», в том числе для пользователя из Москвы.
Для зон с сезонной сменой времени смещение определяется на дату встречи,
а не на текущую дату. Год показывается по правилам [карты экранов](screens.md).

API продолжает передавать startsAt в UTC и отдельный timezone. Эти поля и
часовой пояс срока сдачи имеют разное назначение. Правило касается начала встречи;
оно не назначает новый часовой пояс всем служебным отметкам времени.
Проверить в браузере с другой зоной устройства: FE-03/04/05, QA-01.

## DEC-04 — Развёртывание выполняет пользователь

Сервер уже есть. После готовности контейнеров пользователь сам разворачивает
приложение. Работа команды — воспроизводимая контейнерная поставка, проверенные
команды, `.env.example`, инструкция proxy/Origin/HTTPS, миграций, явного seed,
сохранения данных и проверки готовности. Секреты и реальный адрес не выдумываются.
Образы должны собираться из поставляемых исходников без приватного registry.

Контейнерная готовность и внешняя доступность — разные результаты. Сетевую
проверку `/`, прямых страниц, `/api/docs`, `/api/openapi.yaml` и API проводят после
развёртывания пользователя и получения фактического адреса. До этого её не отмечают
пройденной. Домен, архитектура сервера и настройка внешнего TLS ещё не сообщены;
параметры поставки фиксируются в OPS-01, инструкция — в DELIVERY-01A.

Требование исходников в GitVerse сохраняется. Самостоятельное развёртывание
пользователя не означает, что исходники уже переданы или внешние действия
агентам автоматически разрешены. Передача и финальная сетевая проверка относятся
к DELIVERY-01B; это не поручение агенту заходить на сервер.

## DEC-05 — Первичный охват в пределах города

Пользователь уточнил: ожидаемый охват — примерно один город. Конкретный город,
число активных пользователей, событий и одновременных запросов пока не заданы.
Охват не является оценкой нагрузки и не вводит запрет встреч из других городов.
Поле city, фильтр города и часовой пояс встречи сохраняются. Геолокация и
автоматическое определение города этим решением не добавляются.

При оценке SVG отдельно учитываются объём одной страницы, мобильная сеть,
число просмотров и сложность графики. По результатам обсуждения предел
зафиксирован в DEC-06; правила — [в документе медиа](../architecture/media.md).

## DEC-06 — Предел SVG 128 КиБ

Пользователь уточнил выбранное значение: **128 КиБ (131 072 байта), включительно**.
Размер считается в UTF-8 до XML-разбора и после нормализации. Превышение даёт
413 без изменения прежнего фона. Прежнее решение о 512 КиБ заменено.
Транспортный предел JSON согласован с новым максимумом: 1 МиБ (1 048 576 байт),
с запасом на экранирование строки. Ограничения сложности SVG сохраняются.
API повышен с 0.2.0 до 0.3.0; обновляются схемы, примеры, проверки границ,
тексты интерфейса, проект ограничения БД и требования к proxy/API.

## DEC-07 — Модерация общего справочника направлений

Пользователь выбрал отказ только во включении названия в общий справочник:
PENDING/REJECTED разрешено использовать во встречах. Затем согласовал минимальную
первую версию: одобрение, отказ с причиной и исправление свободного имени.
Объединение дублей и обработка прежних имён/алиасов отложены.

Новое направление — PENDING, встреча публикуется сразу. Общий список содержит
только APPROVED, но поиск/фильтр встреч работают со всеми состояниями.
Повтор того же существующего имени использует прежнюю запись без новой проверки
и сброса отказа. Решение не меняет публикацию/участие; неподходящие встречи
модерируются отдельно. Исправление сохраняет ID и отражается в связанных встречах.

Правила, повторы и границы — [в спецификации направлений](activity-types.md).
API повышен до 0.4.0: административные список/чтение/решение/исправление и сведения
автору опубликованной встречи. Модель БД, экран SCR-20 и задачи обновляются вместе;
реализация приложения и новый экран в макете пока отсутствуют.

## DEC-14 — Будущие подтверждённые встречи первыми, начавшиеся сегодня отдельно

Полный личный список и переход после входа уточнены следующими DEC-15/16.

Пользователь выбрал: «Сначала ближайшие будущие; начавшиеся сегодня — отдельным
компактным блоком». Это уточнение личной главной, а не требование первичных PDF.

- Основной блок: до трёх CONFIRMED/PUBLISHED с startsAt > referenceTime,
  порядок startsAt/event.id ASC. Свободная запись и принятая заявка равноправны;
  createdAt/decidedAt участия не определяют близость встречи.
- Второй компактный блок: CONFIRMED/PUBLISHED с startsAt <= referenceTime
  и датой начала, равной дате referenceTime в зоне встречи. При равенстве времени
  начала событие уже здесь. Начавшиеся вчера исключены, но запись не удаляется.
- PENDING/REJECTED остаются отдельно, организатор не записывается автоматически.
  UNPUBLISHED сохраняется ограниченной сводкой только в полном личном списке.
- Времени окончания нет: «Началась в …», без вывода о завершении или посещении.
- API 0.10.0 расширяет listMyParticipations: eventWindow=UPCOMING/STARTED_TODAY,
  общий referenceTime двух блоков и курсоров, фильтрация/сортировка до пагинации.
  Без окна сохраняются все даты и createdAt/participation.id DESC. Оформление
  отбора прошлых встреч полного списка этим выбором не утверждено.

## DEC-15 — Предстоящие по умолчанию в полном разделе «Участвую»

Пользователь выбрал: «По умолчанию ближайшие будущие по началу; начавшиеся и
более ранние доступны отдельно». Это дополняет DEC-14, который касался главной.

- `/me/events?tab=confirmed` по умолчанию view=upcoming: status=CONFIRMED и
  eventWindow=UPCOMING, startsAt/event.id ASC до пагинации.
- «Начавшиеся» (view=started): status=CONFIRMED, eventWindow=STARTED,
  startsAt <= referenceTime, все дни, startsAt/event.id DESC до пагинации.
  При одинаковом начале ID также DESC. Название не означает завершение/посещение.
- В обоих временных видах только PUBLISHED. Видимая ссылка «Все записи»
  (view=all) запрашивает status=CONFIRMED без eventWindow: все даты и

  Снятые публикации не теряются из личного раздела и не раскрывают время/адрес.
- При смене вида сбрасывается курсор. PENDING/REJECTED остаются во вкладке
  «Заявки», личное авторство — «Организую»; их порядок этим решением не меняется.

сохраняются; view — query существующего экрана, не новый маршрут приложения.

## DEC-19 — Календарный фильтр по местной дате каждой встречи

На вопрос о «7 ноября» в разных поясах пользователь выбрал местное время самой
встречи. API 0.12.0 добавляет listEvents.dateFrom/dateTo, формат YYYY-MM-DD:
нижняя граница включительна, верхняя исключительна. Одиночный день 7 ноября —
dateFrom=2026-11-07/dateTo=2026-11-08. Верхняя включительная дата UI превращается
в следующий календарный день, не в UTC-полночь устройства.

Сервер сравнивает `(starts_at AT TIME ZONE timezone)::date` каждой строки;
вместе с абсолютными from/to все ограничения AND до пагинации/сортировки.
Неверная дата или dateTo <= dateFrom — INVALID_REQUEST. Даты входят в курсор;
смена диапазона требует первой страницы. Зоны устройства/сервера не задают день.

BE-03/FE-03 и QA-01 уточнены, новых таблиц/полей/маршрутов не требуется.
Пресет «Сегодня» для разных зон не вводится этой итерацией: интерфейс задаёт
явные даты и не подменяет их датой устройства. Все прежние решения и весь
объём DEC-17 сохраняются; макет 0.2 не изменяется.
