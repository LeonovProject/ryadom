# Границы продукта

Основание: [первичные источники](../requirements/README.md),
[постановка](../requirements/assignment.md) и [критерии](../requirements/evaluation-criteria.md).
Это рабочая спецификация с редакторскими идентификаторами. При расхождении действует PDF.

## Цель и формат

Рабочий прототип для Столото помогает найти компанию для занятий спортом,
создавать активности и присоединяться к событиям людей и организаций.
Обязателен **адаптивный веб** с интерфейсом, работающей бизнес-логикой,
хранением данных и административным контуром (A-P02, A-P09).

Универсальность относится к разным спортивным направлениям и опыту:
начинающие, любители и профессиональные спортсмены. В примерах — футбол,
шахматы, бег и зарядка; одной дисциплины недостаточно (A-P02, A-P08).

## Обязательный минимум

A-Pxx и C-Pxx обозначают физические страницы соответствующих PDF.

| ID | Требование | Источник |
| --- | --- | --- |
| REQ-WEB | Адаптивный веб, данные, бизнес-логика и административный контур | A-P02, A-P05, A-P09 |
| REQ-ROLES | Три роли: пользователь, организация/сообщество, администратор. Организатор — автор события, а не четвёртая роль | A-P02, A-P04, A-P05 |
| REQ-AUTH | Экраны входа и регистрации обязательны; авторизацию можно имитировать, бизнес-операции должны менять данные | A-P05 |
| REQ-EVENT | Пользователь создаёт и публикует от себя; допущенная организация — от своего имени; событие находится и открывается другим пользователем | A-P03, A-P08 |
| REQ-CARD | Название, описание, спорт; организатор и ссылка на него; дата, время, место и организационная информация; режим записи и условия | A-P03 |
| REQ-SPORT | Готовый список и свой вариант спортивного направления без изменения кода | A-P03, A-P04, A-P08 |
| REQ-JOIN | Два режима в одном прототипе: свободная запись сразу подтверждена; заявка ожидает автора, поддержаны принятие и отказ | A-P04, A-P08 |
| REQ-PARTICIPANTS | Автор видит участников и заявки, пользователь — состояние записи; решения обновляются у обеих сторон | A-P03, A-P04, A-P08 |
| REQ-DISCUSSION | Текстовое обсуждение внутри события, вопрос и ответ автора, различимое авторство. Внешний чат лишь дополняет | A-P05, A-P08 |
| REQ-OPEN-ACCESS | Информация/обсуждение открытой встречи доступны не только записанным; вопрос задаёт любой пользователь платформы | A-P05 |
| REQ-ORG-PROFILE | Название, деятельность и спортивные интересы организации; публичная страница только после допуска | A-P05, A-P06 |
| REQ-ORG-APPROVAL | Представитель подаёт заявку; администратор одобряет/отклоняет, причина отказа видна организации; до допуска нет публикаций от её имени | A-P06, A-P07 |
| REQ-ORG-PUBLISH | После допуска страница публична, события выходят сразу без обязательного повторного согласования | A-P06–A-P08 |
| REQ-ADMIN-SEARCH | Поиск организаций/событий, сведения/состояния; переходы событие → автор/обсуждение, организация → события | A-P06 |
| REQ-ADMIN-EVENT | Администратор удаляет событие или снимает с публикации с причиной для автора | A-P07, A-P08 |
| REQ-ADMIN-MESSAGE | Администратор скрывает/удаляет одно сообщение, сохраняя событие и остальное обсуждение | A-P07 |
| REQ-UNAVAILABLE | Новая запись запрещена и по прямой ссылке; автор и записанные понимают недоступность публикации | A-P07 |
| REQ-USABILITY | Понятность разному цифровому опыту, включая старшее поколение; читаемость и адаптивность браузера | A-P05; C-P06 |
| REQ-DEMO | Вымышленные данные: разные виды спорта, оба режима, организации до/после допуска и заявки; без ручной подготовки экспертом | A-P09 |
| REQ-DELIVERY | Исходники в GitVerse, прототип через сеть, README, доступы трёх ролей, описание сценариев/имитаций/ограничений и презентация | A-P09, A-P10 |

Подробные шаги — в [приёмке](acceptance.md). Функции ещё не реализованы.

## Допустимые упрощения

- Имитация авторизации демоаккаунтами/переключением ролей; экраны входа и регистрации всё равно нужны.
- Адрес или описание места без интерактивной карты; бронирование площадки не требуется.
- Комментарии вместо отдельного мессенджера; файлы и real-time не обязательны.
- Допуск организации без юридической экспертизы, госреестров и обязательных учредительных документов.
- Вымышленные данные; интеграция с системами Столото не нужна.
- Без подтверждения посещения, учёта результатов и судейства.

Основание: A-P04–A-P06, A-P09. Упрощение входа не распространяется на бизнес-логику.

## Дополнительные возможности

Карта, подбор компании, повторения, календарь, лимит мест, очередь, отмена записи,
переносы, уведомления, подписки/иерархия сообществ, геймификация, возврат организации
на доработку, жалобы, блокировки, восстановление публикаций, журнал, аналитика
и отчёты — развитие, а не обязательный чек-лист (A-P04–A-P08).

**Нативное приложение не требуется и не даёт дополнительных баллов** (A-P08).
Мобильная адаптивность веба обязательна. React Native и неспортивные активности
остаются идеями команды вне обязательного объёма и не заменяют разные виды спорта.

## Что оставлено команде

- Серверный стек, хранение, структура проекта, демовход и размещение прототипа.
- Поля сверх минимума, каталог/фильтры и обработка пользовательских названий спорта.
- Названия статусов и схема данных, обеспечивающие обязательное поведение.
- Ограничения обсуждения/информации событий по заявке, отображение профилей и контактов.
- Судьба существующих записей после модерации при запрете новой записи и понятной недоступности.
- Выбранные дополнительные улучшения и правила их работы.

Три роли, внутреннее обсуждение, права допущенной организации и запрет записи
по прямой ссылке больше не являются неизвестными условиями.

Варианты решений описаны в [техническом проекте](../architecture/README.md),
[правах и состояниях](../architecture/access-and-states.md),
[модели данных](../architecture/data-model.md) и [проекте API](../contracts/api-proposal.md).
Это предложения для обсуждения. Обязательные требования выше не изменены;
предложенные ограничения не считаются утверждёнными правилами продукта.

[Карта экранов](screens.md) описывает предлагаемые страницы и состояния,
[пользовательские пути](user-flows.md) связывают их с S1–S6/A1–A6. Главная с hero,
компоновка кабинетов и минимальный публичный профиль — предложения интерфейса,
а не новые обязательные критерии.

## Бренд и технологии

«Рядом», красно-белая палитра и React для веба — договорённости пользователя.
Постановка не навязывает конкретный стек. Брендбук 1.2 применяется для оформления;
[связь с требованиями](../../brandbook/requirements-alignment.md) помогает читать примеры.
Брендбук не имеет приоритета над PDF.
