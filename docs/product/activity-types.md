# Направления встреч и общий справочник

Дата: 2026-10-19. Статус: **принято пользователем, DEC-07; реализация впереди**.
Основание — готовый или свой вид спорта без правки кода ([REQ-SPORT](scope.md)).
Модерация справочника — выбранное улучшение команды, а не дополнительный критерий
PDF. Объединение дублей отложено. Формы данных — только в
[OpenAPI 0.13.0](../../packages/contracts/openapi.yaml).

## Видимость и использование

Модерация определяет включение названия в общий список выбора. Встреча со своим
направлением публикуется сразу по обычным правам автора. Статус направления
независим от допуска организации, публикации события и участия.

| catalogStatus | Подпись | Общий список выбора | Использование во встрече |
| --- | --- | --- | --- |
| PENDING | Ожидает проверки | Нет | Разрешено |
| APPROVED | В справочнике | Да | Разрешено |
| REJECTED | Не включено в справочник | Нет | Разрешено |

Название любого состояния видно в опубликованной встрече. Поиск q учитывает его,
фильтр activityTypeId и создание по известному ID работают для всех состояний.
Отсутствие в списке не означает закрытые данные или запрет. Публичный DTO
направления по-прежнему содержит только id/name.

## Создание и повторное использование

1. Автор выбирает APPROVED из списка либо вводит свой вариант.
2. Имя проходит Unicode NFC, trim и свёртку пробелов. Отображаемое имя сохраняет
   регистр; normalized_name использует единый серверный алгоритм приведения регистра.
   Непустое имя — максимум 100 символов до/после нормализации. Синонимы не объединяются.
3. Совпавшее существующее имя используется с прежним ID независимо от catalogStatus.
   PENDING/REJECTED не сбрасываются, новая проверка не создаётся.
4. Новое имя создаёт PENDING с фактическим аккаунтом-создателем. Направление и
   событие сохраняются одной транзакцией; ошибка события откатывает оба изменения.
   Одновременное создание одинакового имени разрешается UNIQUE и повторным чтением.
5. Подготовленные seed-направления — APPROVED. Клиент не назначает catalogStatus.

В опубликованной карточке автор получает activityTypeReview: состояние и причину
невключения. Это личный автор либо текущий ответственный организации-автора,
даже если направление создал другой человек. Другие читатели получают null,
включая ADMIN без авторства на публичном маршруте. Ограниченная карточка
UNPUBLISHED не расширяется; ADMIN получает сведения через свою очередь.

## Действия администратора

Очередь показывает название, состояние, создателя, даты, проверяющего, причину
и число всех связанных встреч. У seed создатель/проверяющий отсутствуют.
Интерфейс начинает с PENDING; API без фильтра возвращает все состояния.

| Действие | Правило |
| --- | --- |
| Одобрить | PENDING → APPROVED; без причины |
| Исправить и одобрить | Свободное имя и APPROVED сохраняются атомарно |
| Не включать | PENDING → REJECTED; непустая причина, максимум 2000 символов |
| Исправить имя | Любое состояние и seed; решение сохраняется |
| Смотреть встречи | Административный список с activityTypeId, включая снятые |

Решение разовое для первой версии. Повторная подача, возврат в PENDING и пересмотр
противоположного решения не входят в неё. Использование REJECTED не создаёт заявку.

При исправлении ID сохраняется, связанные встречи после чтения показывают новое
имя. Публикации и участия не меняются, ссылки фильтра по ID работают.
Уникальность normalized_name охватывает все состояния и seed. Занятое другим ID
имя даёт 409 ACTIVITY_TYPE_NAME_CONFLICT без частичного изменения имени/решения.
Объединения и удаления нет.

Прежнее написание после переименования не резервируется: истории имён/алиасов
в первой версии нет. Ввод освободившегося написания может создать новое PENDING.
Это граница отложенного объединения, не обещание поиска синонимов.

## Конкуренция и повторы

Проверка и изменение выполняются под блокировкой строки направления. name и
normalized_name обновляются вместе; UNIQUE защищает коллизии разных направлений.
expectedName передаётся из прочитанного DTO и сравнивается после нормализации
для отображения, с учётом регистра.

- Новое решение PENDING требует совпадения expectedName; иначе 409 ACTIVITY_TYPE_CHANGED.
- APPROVE с name атомарно исправляет имя и сохраняет решение/проверяющего/время.
  REJECT не принимает name.
- Повтор того же решения — 200 без перезаписи проверяющего/времени. У REJECT
  совпадает нормализованная причина, у APPROVE переданное name совпадает с текущим.
  expectedName не мешает такому повтору. Противоположное решение, другая причина
  или отличающееся name дают 409 DECISION_CONFLICT.
- Переименование в уже текущее отображаемое имя — 200 без смены updatedAt.
  Иначе проверяются expectedName и свободность normalized_name.
- Два одинаковых решения возвращают сохранённый результат; противоположные дают
  одно решение и конфликт. Два направления не получают одно normalized_name.

После неизвестного сетевого результата направление читается по ID через
adminGetActivityType, даже если оно уже исчезло из отфильтрованной очереди.
Затем обновляются очередь и связанные данные.
Интерфейс не сообщает об успехе до подтверждения. После изменений обновляются
очередь, общий список, карточки/списки встреч. Другие пользователи видят результат
после собственного чтения; push не добавляется.

## Пример и будущая проверка

«Сапбординг» создаётся как PENDING вместе с опубликованной встречей. Другой человек
находит встречу и записывается по обычным правилам. После отказа во включении
название остаётся во встрече и доступно для новых встреч; в общем списке его нет.
Неприемлемую встречу администратор снимает отдельно, с причиной.

Проверить новый спорт без правки кода/ожидания; обе ветки решения; повтор отказа
при новом событии; поиск и фильтр неутверждённого направления; исправление во всех
связанных встречах; сохранение после перезапуска; коллизии/конкурентные действия;
закрытые сведения и запрет административных операций для USER.
