# Аутентификация — DEC-20

Статус: **принято для MVP** 2026-10-19; AUTH-01/BE-02 реализованы и проверены
20 октября — [отчёт BE-02](../../apps/api/internal/modules/auth/README.md).
Пользователь выбрал email и пароль, без подтверждения почты и восстановления
пароля, с JWT. Это заменяет демопереключение и регистрацию только по имени.
Постановка допускает имитацию входа (A-P05); настоящий вход — решение команды.
Транспорт — [API 0.13.0](../contracts/api-v1.md), формы —
[OpenAPI](../../packages/contracts/openapi.yaml), блокировка — [DEC-21](../product/account-blocking.md).

## Вход и регистрация

| Действие | Контракт и результат |
| --- | --- |
| Регистрация | POST /api/v1/auth/register, операция register, RegisterInput: email, password, displayName, presetId. Один commit создаёт USER/ACTIVE, начальный PRESET/APPROVED/revision=1 и сессию; 201 Me и cookie только после commit |
| Вход | POST /api/v1/auth/login, операция login, LoginInput: email/password; проверка пароля и ACTIVE, затем 200 Me и новая cookie. Успех заменяет текущую сессию этого браузера; другие устройства сохраняются |
| Текущий аккаунт | GET /api/v1/me: публичные данные, приватный email, роль, срок сессии и собственные организации. Чтение не продлевает вход |
| Выход | POST /api/v1/auth/logout: удалить текущую сессию и очистить cookie, 204 также без действующего входа или при BLOCKED. Origin обязателен |

Регистрация и вход работают независимо от DEMO_MODE. Прежние demo-profiles,
demo-login и demo-register исключены из API; нет публичной кнопки выдачи ADMIN
по одному demoKey. demo_key остаётся стабильным служебным ключом сида, не паролем.
Выход/смена аккаунта очищают весь персональный кеш; ошибка нового входа не
заменяет прежнюю действующую сессию. Допустимый returnTo имеет приоритет, иначе
открывается персональная главная /. Участие/вопрос/жалоба сами не отправляются.

Email — ASCII, 3..254 символа, корректный адрес без пробелов. Клиент обрезает
пробелы вокруг поля; API отклоняет их с 422 /email. Весь адрес приводится к
нижнему регистру перед сохранением и поиском; UNIQUE accounts(email) защищает
от параллельного создания дублей. Точки/суффиксы + не преобразуются. Email не
подтверждён и не доказывает владение почтовым ящиком; письма не отправляются.

Пароль регистрации — 15..128 Unicode code points; пароль входа — 1..128.
Пароль не trim/normalize, пробелы и Unicode допустимы, ввод не обрезается молча.
Нет обязательной смеси специальных символов/регистров. Хранится Argon2id PHC:
m=19456 КиБ, t=2, p=1, криптографически случайная соль 16 байт и хеш 32 байта.
Соль отдельная для каждого хеша. Пароль, PHC и токен не возвращаются в DTO и
не попадают в логи. Подтверждение пароля на форме — клиентская проверка, не поле API.

Одинаковые displayName разрешены. Имя и обязательный готовый аватар сохраняются
по [DEC-11/12](../product/registration.md); свой SVG загружается позднее в профиле.
Пустой каталог блокирует только новую регистрацию. Вход ранее созданными
аккаунтами доступен без готовых картинок. Смена email/пароля, восстановление,
подтверждение почты и внешние провайдеры в MVP не входят.

## JWT и серверный отзыв

- Cookie: ryadom_session; HttpOnly; Path=/api/v1; SameSite=Lax; Max-Age=86400;
  без Domain. Secure обязателен для сетевого HTTPS; для локального HTTP выключен
  явно. JWT не выдаётся полем JSON и не сохраняется в localStorage.
- Подпись только HS256; typ=ryadom-session+jwt. Алгоритм задан конфигурацией
  валидатора, не выбирается заголовком токена. none и другие алгоритмы отклоняются.
  AUTH_JWT_SECRET — base64 минимум 32 случайных байт, только у API, без значения
  по умолчанию или секрета в Git/образе/вебе. При отсутствии/неверной конфигурации
  API не запускается. Ключ сохраняется при обычном пересоздании контейнера.
- Обязательные claims: iss=ryadom-api, aud=ryadom-web, sub=accounts.id,
  jti=sessions.id, целочисленные iat/exp (Unix seconds), exp=iat+86400.
  Срок 24 часа без refresh и скользящего продления. iat не может быть в будущем
  более чем на 30 секунд; при now >= exp токен истёк, продления льготой нет.
- Строка sessions содержит ID, account_id, SHA-256 полного подписанного JWT
  в token_hash и created_at/expires_at, согласованные с iat/exp. JWT строится
  для новой строки внутри операции, cookie выдаётся только после commit.
  Проверяются подпись/typ/claims, существование аккаунта, ACTIVE, затем совпадение
  jti/sub/хеша/срока в актуальной sessions. Роль и владение берутся из БД.
- Каждое защищённое обращение читает текущее состояние в БД; Redis и отдельный
  список отозванных токенов не требуются. Подпись JWT без проверки sessions не
  является достаточным доступом. Выход удаляет одну сессию, блокировка и reset — все
  соответствующие сессии. Разблокировка никогда не восстанавливает старые JWT.
- Все изменяющие запросы, включая вход/регистрацию/выход, сохраняют проверку
  допустимого Origin. Один origin веба и API; браузер отправляет cookie через
  credentials: same-origin. HTTPS требуется для сетевого входа с паролем.

## Ошибки и ограничения попыток

| Ситуация | Ответ и поведение |
| --- | --- |
| Неверная пара email/пароль | 401 INVALID_CREDENTIALS, одинаковый текст для неизвестного адреса и неверного пароля. Для неизвестного email выполнить проверку фиксированного фиктивного Argon2id-хеша, не раскрывать существование по короткому пути |
| Правильный пароль BLOCKED | 403 ACCOUNT_BLOCKED без создания сессии; при неверном пароле всё равно INVALID_CREDENTIALS |
| Занятый email регистрации | 409 EMAIL_TAKEN, /email; предложить вход или другой адрес, ничего частично не сохранять |
| Закрытый маршрут без cookie | 401 AUTH_REQUIRED |
| Неверный/истёкший JWT, удалённый аккаунт или отозванная сессия ACTIVE | 401 SESSION_EXPIRED, очистить cookie |
| Подписанный ещё не истёкший JWT аккаунта BLOCKED | 403 ACCOUNT_BLOCKED до проверки роли/предметных прав, даже после удаления sessions; очистить cookie. После разблокировки тот же JWT даст SESSION_EXPIRED |
| Слишком много попыток | 429 RATE_LIMITED с Retry-After в секундах, минимум 1; никакого автоматического POST retry |

Неверный Origin даёт 403 CSRF_REJECTED до проверки пароля. На публичных чтениях
cookie игнорируется; optional-session без cookie разрешает гостя, с неверной
даёт 401, с JWT заблокированного аккаунта — 403. После очистки cookie общедоступный
ресурс можно открыть как гостю. ACCOUNT_BLOCKED на защищённом или optional-session
запросе очищает персональный кеш;
интерфейс показывает «Аккаунт заблокирован», а не обещает помощь несуществующей
службы поддержки. Ошибка login не очищает/заменяет прежнюю сессию другого
аккаунта: это отказ нового входа, а не отзыв текущего. Logout остаётся доступен
для очистки cookie при любом статусе.

До дорогой проверки/создания Argon2id применяются ограничения одного API:
login — до 10 запросов на пару IP/канонический email и 100 на IP за 15 минут;
register — до 20 на IP за час. Считаются все попытки; окно начинается с первого
запроса, успешный вход не обнуляет счётчик. При превышении любого окна Retry-After
равен максимуму оставшегося времени ограничивающих окон, округлённому вверх.
Счётчики в TTL-хранилище процесса ёмкостью 10000 ключей; при рестарте сбрасываются.
Один экземпляр API — граница MVP. Удалять живые лимиты ради приёма новых ключей
нельзя: при исчерпании ёмкости вернуть 429 до ближайшего освобождения.
IP берётся из соединения/доверенного Nginx, который перезаписывает forwarding
заголовки; произвольный X-Forwarded-For не считается адресом клиента.

## Транзакции и конкуренция с блокировкой

После общего барьера demo_state (DEC-13) защищённая операция берёт accounts
действующего лица FOR SHARE и проверяет свежий статус/сессию; держит этот замок
до конца транзакции. Затем идут предметные замки. Login проверяет пароль и ACTIVE
под тем же замком; создание сессии не может проскочить после commit блокировки.
Регистрация вставляет новый ACTIVE-аккаунт и связанные данные одной транзакцией;
конкурирующий email разрешает UNIQUE, не предварительная проверка в памяти.

Блокировка: demo_state FOR SHARE → accounts ADMIN FOR SHARE → предварительная
проверка существования/неизменяемой роли цели → только USER FOR UPDATE → повторная
проверка роли/expectedRevision → статус и удаление sessions → commit.
Запрос замка цели содержит system_role=USER; ADMIN отклоняется до попытки его
эксклюзивной блокировки. Иначе два ADMIN могли бы ждать друг друга ещё до отказа.
Logout после барьера берёт accounts предъявленной действительной сессии FOR SHARE
до удаления sessions, но BLOCKED не запрещает очистку/выход. Изменяемый статус
проверяется после ожидания. Проверки только в middleware до предметных ожиданий
недостаточно. Операция USER либо завершится до commit блокировки, либо будет
отклонена после неё; уже выполненные действия не откатываются задним числом.

## Подготовленные доступы и сброс

Это исключительно вымышленные данные будущего сида, не настоящие секреты:

| demo_key | Email | Пароль для демонстрации | Контекст |
| --- | --- | --- | --- |
| alex | alex@example.test | Ryadom-Alex-2026! | USER |
| anna | anna@example.test | Ryadom-Anna-2026! | USER, представитель организаций |
| marina | marina@example.test | Ryadom-Marina-2026! | ADMIN |

Сид сохраняет для них Argon2id-хеши, не исходные пароли в accounts. После reset
UUID новые, email/demo_key/пароли прежние; все сессии удалены. ADMIN входит обычным
login и сверяет resetId по DEC-13. Добавляется отдельный BLOCKED USER для проверки;
основные три доступа остаются ACTIVE и пригодны для S1–S6. Обычный запуск не
пересоздаёт аккаунты и не снимает блокировки. DEMO_MODE управляет демосбросом,
а не наличием пароля или правами регистрации. Публичные демонстрационные доступы
не следует использовать для иных данных; автоматическое развёртывание не разрешено.

## Основания

- [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html): правила проверки JWT.
- [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#jwt): проверка claims и досрочный отзыв доступа.
- [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): cookie и защита сессии.
- [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html): пароль, одинаковые ошибки и ограничения попыток.
- [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): Argon2id и параметры хеширования.

Срок JWT, claims, выбранный HS256, лимиты попыток и серверная таблица активных
сессий — конкретные решения этого проекта. Документ не подтверждает работу входа.
