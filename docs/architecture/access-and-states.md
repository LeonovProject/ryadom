# Права доступа и состояния API 0.13.0

Статус: **зафиксировано в контракте 0.13.0; реализация отсутствует**. Основание —
[первичные требования](../requirements/README.md), [границы](../product/scope.md)
и [приёмка](../product/acceptance.md). Модель связана с
[данными](data-model.md) и [API](../contracts/api-v1.md). Транспортные поля —
в [OpenAPI](../../packages/contracts/openapi.yaml).

## Роли и контексты

В продукте три роли: пользователь, организация/сообщество и администратор.
Технически входят люди под аккаунтами. `system_role=ADMIN` даёт модерацию;
связь `organizations.owner_account_id` даёт представительство организации.
Контекст организации не передаёт ей полномочия администратора. Само наличие
ADMIN не даёт права решать по заявкам чужого мероприятия.

Организатор — автор конкретного события: личный аккаунт либо организация,
представленная своим ответственным. Предлагается один ответственный на профиль;
переключение контекста влияет на авторство новой встречи, но не на системные права.
Администратор может действовать как обычный пользователь в собственных встречах.

## Матрица действий

Все изменения проверяются API; скрытие кнопки не считается ограничением доступа.

| Действие | Посетитель без сессии | Пользователь | Ответственный организации | Администратор |
| --- | --- | --- | --- | --- |
| Каталог и опубликованная карточка | Да | Да | Да | Да |
| Публичная страница одобренной организации | Да | Да | Да | Да |
| Читать опубликованное обсуждение | Да | Да | Да | Да |
| Задать вопрос / записаться | Нет | Да | Как человек со своего аккаунта | Как человек со своего аккаунта |
| Создать личное событие | Нет | От себя | От себя в личном контексте | От себя |
| Публиковать от организации | Нет | Нет, без владения | Только от своей и после допуска | Только при отдельном владении и допуске |
| Смотреть непубличный профиль/заявку организации | Нет | Только при владении | Своя организация | Все |
| Смотреть заявки участников | Нет | Если автор | Свои события организации | Если автор; модерация не даёт это право автоматически |
| Принять/отклонить заявку участника | Нет | Если автор | Свои события организации | Только если автор |
| Одобрить/отклонить организацию | Нет | Нет | Нет | Да |
| Снять чужое событие с причиной | Нет | Нет | Нет | Да |
| Скрыть отдельное сообщение | Нет | Нет | Нет | Да |
| Решить/исправить направление общего справочника | Нет | Нет | Нет | Да |

Предлагаемая простая политика: опубликованные события обоих режимов открыты
для чтения. Любой вошедший пользователь может задать вопрос и до записи.
Для событий по заявке постановка допускает ограничения; здесь предлагается
ими не пользоваться. Списки ожидающих/отклонённых заявок публично не выдаются.
В карточке достаточно числа подтверждённых участников; полный список и заявки
доступны автору, собственная запись — её владельцу.

Публичный профиль человека содержит ID, отображаемое имя и avatarUrl/null. Служебная роль,
сессии и закрытые данные в него не входят. Создание профиля организации само
по себе не делает страницу публичной: необходим APPROVED у заявки.

## Справочник направлений — отдельное состояние

[DEC-07](../product/activity-types.md): PENDING/APPROVED/REJECTED направления
управляют включением в общий список, не допуском организации или публикацией встречи.
Только APPROVED перечисляется в listActivityTypes. Имя/ID любого состояния
разрешены при создании встречи и в фильтрах; REJECTED не является запретом.
Новое имя — PENDING вместе с немедленно опубликованной встречей, повтор имени
не сбрасывает отказ. Список/решение/исправление доступны только ADMIN.
Автор опубликованной встречи получает activityTypeReview; другим на публичном
маршруте возвращается null. Переименование сохраняет ID/решение/участия.
Коллизия имени — конфликт без слияния; объединение и алиасы отложены.

## Допуск организации

| Состояние | Что видит организация | Публичная страница / публикация |
| --- | --- | --- |
| Заявки нет | Свой профиль и действие подачи | Недоступны |
| PENDING | «На проверке» | Недоступны |
| APPROVED | «Допущена к публикации» | Доступны без повторной модерации события |
| REJECTED | «Допуск не предоставлен» и причина | Недоступны |

Переходы: нет заявки → PENDING → APPROVED или REJECTED. Решение принимается один
раз. Повтор того же решения возвращает результат, противоположное даёт конфликт.
Повторная подача и возврат на уточнение — отдельные дополнительные функции;
их нет в базовом проекте, хотя брендбук содержит возможные подписи таких состояний.

## Публикация события

Предлагается публикация сразу при успешном создании. Для личного автора отдельного
допуска нет. Для организации проверяется допуск и владение.

PUBLISHED → UNPUBLISHED выполняет администратор с причиной для автора.
Используется снятие с публикации как один из двух разрешённых постановкой вариантов.
Физическое удаление, восстановление, черновик и самостоятельная отмена автором
не входят в базовую реализацию.

После снятия:

- событие исключено из каталога для записи и публичного списка событий организации;
- присоединение, подача заявки, новые сообщения и решения по старым заявкам запрещены;
- причина снятия доступна автору и администратору;
- автор, администратор и обладатели любой собственной записи, включая PENDING и
  REJECTED, видят ограниченную карточку со статусом недоступности; остальные получают 404;
- существующие записи сохраняют статус, но показываются вместе с признаком
  недоступной публикации. Подтверждённый участник не получает ложного обещания,
  что встреча состоится. Автоматической отмены или внешней рассылки нет.

Ограниченная карточка содержит ID, название, состояние публикации, собственное
участие и `canJoin=false`. Причина добавляется только автору/администратору.
Обсуждение снятого события читает только администратор через
`GET /admin/events/{eventId}/messages`; публичный маршрут даёт 404.
Эти ограничения — зафиксированный выбор команды для версии 0.13.0.
Невозможность новой записи, в том числе по прямой ссылке, обязательна по PDF.

## Участие

До начала OPEN создаёт CONFIRMED сразу. APPROVAL создаёт PENDING; автор меняет его на
CONFIRMED или REJECTED только до начала. Один аккаунт имеет не больше одной записи на событие.
Авторство определяется по событию и текущему владению организацией.

Повтор присоединения возвращает существующую запись, не сбрасывает отказ и не
подтверждает ожидание. Для снятого события проверка доступности выполняется
раньше возврата существующей записи: изменяющий запрос получает EVENT_UNAVAILABLE.
При опубликованной встрече следующая проверка — серверное now >= startsAt:
joinEvent и decideParticipation получают 409 EVENT_STARTED, включая повторы.
Часы проверяются после блокировок непосредственно перед операцией.
Начало сохраняет публикацию, существующее участие и право автора читать состав.
canManageParticipants отвечает за чтение; canDecideParticipations — за решения
только до начала. В опубликованной карточке EVENT_STARTED имеет приоритет перед
прочими joinBlockedReason. PENDING не превращается автоматически в отказ.
Обсуждение опубликованной встречи после начала доступно по прежним правам.
Граница, интерфейсные пояснения и будущие проверки — [DEC-01](../product/decisions.md).
Отзыв, отмена и повторная подача после отказа отдельно не реализуются.

## Обсуждение и модерация сообщения

В опубликованном событии пользователь отправляет обычный текст, организатор
отвечает таким же сообщением. Автор каждого сообщения различим. Организатор
организации отвечает своим аккаунтом с отметкой связи с автором мероприятия.

Администратор переводит VISIBLE → HIDDEN и может восстановить HIDDEN → VISIBLE
без причины (DEC-08). У остальных вместо скрытого текста — нейтральная
подпись «Сообщение скрыто» на прежнем месте. Исходный текст виден
только администратору через отдельный административный маршрут. Публичный
маршрут не возвращает body у HIDDEN даже администратору. Остальное обсуждение и событие сохраняются. Вложения,
отдельные диалоги и WebSocket не входят в базовый проект.

[Жалобы DEC-08](../product/reports-and-moderation.md) на опубликованную встречу
или видимое чужое сообщение доступны вошедшему без обязательной записи.
Одна запись аккаунта/цели за всё время; OPEN/RESOLVED/DISMISSED не меняют роли,
публикацию и участие. Автоматического скрытия нет. ADMIN скрывает/восстанавливает
одно сообщение, снимает встречу с обязательной причиной или отклоняет жалобы
без изменения видимости. Скрытие закрывает жалобы только сообщения; снятие —
только прямые жалобы встречи. Восстановление не открывает жалобы заново и не
восстанавливает публикацию. Версии запросов защищают от устаревших решений.

## Аутентификация и блокировка — DEC-20/21

[Правила входа](authentication.md) заменяют демовыбор: email/пароль,
JWT в HttpOnly cookie на 24 часа, серверные sessions и проверка ACTIVE на каждом
защищённом запросе. Существующий пользователь может повторно войти после выхода.
Подготовленные аккаунты трёх контекстов используют обычные учётные данные;
demo_key не выдаёт роль и не служит паролем. Регистрация не создаёт ADMIN.

[Блокировка USER](../product/account-blocking.md) завершает все его сессии и
запрещает новый вход/действия, включая собственные организации. ADMIN защищён
от блокировки. Разблокировка требует нового входа, прежние JWT не оживают.
Публичное чтение гостем доступно. Контент, допуск организаций и участия сохраняются;
перед заявкой на встречу интерфейс предупреждает о недоступном организаторе.

PublicAccount раскрывает только id/displayName/avatarUrl/isBlocked;
OrganizationOrganizer/PublicOrganization — ownerIsBlocked. Email только в Me
и административном AdminAccount. Последний содержит status/revision/blocked-поля.
На защищённых/optional-session маршрутах JWT BLOCKED даёт 403 ACCOUNT_BLOCKED
с очисткой cookie; обычный USER на административном маршруте — 403 FORBIDDEN.
Origin и очистка персонального кеша сохраняются; детали/приоритет ошибок — в API.

Общий барьер DEC-13 идёт первым; защищённая операция держит accounts актёра
FOR SHARE до конца транзакции. Блокировка берёт USER-цель FOR UPDATE. Проверка
актуальных прав после ожидания обязательна, уже выполненное не откатывается.

## Готовый и личный аватар DEC-09/10

По DEC-12 готовый presetId обязателен в новой регистрации; отсутствие/null и
пустой каталог не дают создать профиль. Это не запрет сброса картинки в уже
существующем аккаунте или NONE у подготовленных демопрофилей.

Публичный avatarUrl задан для готового PRESET либо личного CUSTOM/APPROVED.
NONE/EMPTY и личные PENDING/HIDDEN — заглушка;
владелец и ADMIN видят приватный SVG через отдельные маршруты с проверкой версии.
Новое изображение всегда PENDING, даже если прежнее было одобрено. ADMIN одобряет/
скрывает без причины; одобрение HIDDEN восстанавливает файл. Изменения сериализуются
по аккаунту и account_avatars; expectedRevision не позволяет старой форме решить
судьбу нового файла. PRESET не входит в очередь и даёт 404 прямых действий ADMIN.
Выбор готового очищает текущий личный SVG; следующая загрузка снова PENDING.
Готовый ID проверяется по общему manifest; неизвестный не меняет выбор, а ранее
выбранный исключённый ID даёт заглушку без автоматического изменения БД.
Подробно — [SVG-аватары](../product/avatars.md).

## Сброс демобазы DEC-13

Только ADMIN при DEMO_MODE=true и правильном Origin. Подтверждение СБРОСИТЬ
не выдаёт прав обычному пользователю. После эксклюзивного барьера снова
проверяются сессия/ADMIN и generation/seedVersion/resetId. Успех завершает все
сессии и возвращает квитанцию; ошибка откатывает всё. Повторная авторизация
подготовленным профилем ADMIN позволяет прочитать последнюю квитанцию, но не
повторить старое удаление. Общий shared-барьер до предметных блокировок обязателен
для всех сессионных/предметных операций. [Полные правила](../product/demo-reset.md).
