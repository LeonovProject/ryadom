# Общий контракт API Рядом 0.13.0

Статус: **зафиксирован для параллельной реализации по поручению пользователя**.
Приложений, API и БД пока нет. Этот пакет содержит спецификацию и проверяемые
примеры; он не предоставляет работающие бизнес-операции.
После реализации по требованию пользователя Swagger UI будет доступен на адресе
прототипа по `/api/docs`, текущая спецификация — `/api/openapi.yaml`.
UI использует этот же файл, отдельная схема не поддерживается; подробнее —
[требование Swagger UI](../../docs/development/api-documentation.md).

- [openapi.yaml](openapi.yaml) — единственный источник маршрутов и транспортных DTO:
  60 операций и 100 схем, включая обязательные сценарии, CATALOG-01, REPORTS-01, MEDIA-01 и healthcheck.
- [Интеграционные правила](../../docs/contracts/api-v1.md) — права, состояния,
  пагинация, ошибки, повторы, переходы экранов и обновление клиентских данных.
- [http-cases.json](examples/http-cases.json) — 280 именованных HTTP-примеров.
  Указаны operationId, path/query, тело запроса, HTTP-статус и ответ.
  В `svgTooLarge` поле requestBodyRecipe задаёт размер строки SVG; проверка
  создаёт её в памяти, чтобы не хранить большой искусственный файл в репозитории.
- [invalid-payloads.json](examples/invalid-payloads.json) — 64 примера,
  которые должны отклоняться схемой, включая утечку скрытого текста/закрытых полей.
- [oapi-codegen.yaml](oapi-codegen.yaml) — конфигурация Go-моделей и интерфейсов.
- [tooling.json](tooling.json) — проверенные версии инструментов генерации.
- [avatar-presets.json](avatar-presets.json) — единый каталог готовых SVG:
  1 изображение «Спутник» по DEC-22; [исходник и подключение](avatar-presets/README.md).
  Проверка сверяет схему, ID/URL, UTF-8, размер и наличие файлов; XML allowlist
  применяется отдельно при подготовке SVG в MEDIA-01F.

## Как разделить работу

Координатор владеет `openapi.yaml` и примерами. Бэкенд реализует зафиксированные
operationId, статусы и DTO; фронтенд использует те же схемы и примеры для загрузки,
успешных и ошибочных состояний. Назначение исполнителей и запуск разработки
остаются отдельным шагом, описанным [в процессе](../../docs/development/multi-agent-workflow.md).

Фронтенд может строить локальные моки из примеров, выбирая нужный `name` явно.
Фикстуры не являются сервером и не моделируют переходы данных между пользователями.
Для основного сценария после интеграции используются только реальные операции API.

Идентификаторы аккаунтов/встреч, строки cookie и даты в примерах вымышлены.
Статический URL `ryadom-companion.svg` соответствует подготовленному исходнику;
серверные URL личных аватаров/фонов пока не обслуживаются. Для
контрактных тестов часы фиксируются на `2026-11-01T09:00:00Z`. В живом демонаборе
даты готовятся относительно даты демонстрации; примеры не являются seed для БД.
Временные примеры имеют `preconditions`: часы, начало и контекст субъекта/публикации.
В них `now` заменяет общую дату фикстур. Валидатор проверяет формы запросов/ответов,
а не исполняет эти предусловия. Реальная проверка границы, блокировок и отсутствия
изменений БД относится к BE-07/QA-01. Правила — [DEC-01](../../docs/product/decisions.md).

## Проверка спецификации и примеров

Из корня репозитория, Python 3.12 в отдельном окружении:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r scripts/requirements-contracts.txt
.venv/bin/python scripts/check_api_contract.py
```

Это проверенные команды инструментов контракта, не команды запуска приложения.
Проверяются OpenAPI 3.0.3, уникальные operationId/параметры, схемы всех примеров,
покрытие успешных HTTP-статусов, отклонение отрицательных примеров, права в
метаданных операций и байтовая граница SVG. XML-безопасность, реальные права,
транзакции, хранение и контейнерный запуск этим не проверяются.

Проверки без сторонних библиотек остаются прежними:

```bash
python3 scripts/check_repository.py
git diff --check
```

## Проверенная генерация в отдельную папку

Установка инструментов выполняется отдельно; версии закреплены в tooling.json.
Из корня репозитория, после установки oapi-codegen 2.4.1 и openapi-typescript 7.6.1:

```bash
oapi-codegen -config packages/contracts/oapi-codegen.yaml -o /tmp/ryadom-api.gen.go packages/contracts/openapi.yaml
openapi-typescript packages/contracts/openapi.yaml -o /tmp/ryadom-api.d.ts
```

При реализации координатор назначит окончательные пути генерации в Go API и
`packages/api-client`; сами производные не редактируются вручную. Исходный SQL
и типы pgx/sqlc не становятся транспортными DTO.

## Версия и изменения

Версия 0.1.0 — исходный интеграционный контракт. Версия 0.2.0 добавила
обязательный EventCapabilities.canDecideParticipations, причину EVENT_STARTED и
закрыла joinEvent/decideParticipation при now >= startsAt, включая повторы.
canManageParticipants сохраняет право автора читать состав после начала.
Версия 0.3.0 по DEC-06 уменьшила SVG до 128 КиБ (131072 UTF-8 байта)
до/после нормализации, JSON-тело — до 1 МиБ (1048576 байт). Граница включительна;
131073 байта SVG дают 413 без изменения фона. Обновлены примеры и проверки.
Версия 0.4.0 по DEC-07 добавила административные список/чтение/решение/исправление
направлений, обязательный nullable PublishedEventDetail.activityTypeReview для автора
и фильтр adminListEvents.activityTypeId. Общий listActivityTypes теперь только APPROVED;
PENDING/REJECTED разрешены в createEvent/поиске. Добавлены ACTIVITY_TYPE_NAME_CONFLICT
и ACTIVITY_TYPE_CHANGED, expectedName защищает от устаревшего исправления.
Объединение и алиасы отложены. Правила — [в спецификации направлений](../../docs/product/activity-types.md).
Версия 0.5.0 по DEC-08 добавила reportEvent/reportMessage,
adminGetMessage, adminRestoreMessage и отклонение жалоб на обе цели. adminHideMessage
теперь требует MessageModerationInput {expectedRevision}. AdminMessage/AdminEvent
получили обязательные версии и OPEN-счётчики. hasOpenReports фильтрует административные
списки. Старые команды не отменяют новые решения; закрытые жалобы не открываются.
Причины жалобы/скрытия/восстановления не нужны, причина снятия встречи сохраняется.
Правила — [спецификация модерации](../../docs/product/reports-and-moderation.md).
Версия 0.6.0 по DEC-09 заменила готовый набор личным SVG с модерацией.
PublicAccount/NullablePublicAccount используют avatarUrl вместо avatarId. listAvatars/
setAvatar и старые схемы выбора исключены. Добавлены upload/reset/state, публичное
изображение APPROVED, private preview владельца/ADMIN, очередь и решения без причины.
revision и expectedRevision защищают от решения по уже заменённому файлу;
128 КиБ SVG/1 МиБ JSON проверяются для обоих видов изображений. Правила —
[SVG-аватары](../../docs/product/avatars.md).
Версия 0.7.0 по DEC-10 дополнила личную загрузку готовым выбором:
listAvatarPresets/selectPresetAvatar, обязательные source/presetId в AvatarState,
статический avatarUrl для PRESET. Готовый вариант доступен сразу, очередь ADMIN
только CUSTOM. Один текущий выбор, неизвестный ID не меняет его, а исключённый
из manifest ранее выбранный даёт заглушку. По последующему DEC-22 manifest
содержит реальный `ryadom-companion.svg`; примеры согласованы с его ID/label/URL.
Версия 0.8.0 по DEC-11 добавила необязательный nullable presetId
в DemoRegisterInput. Один запрос создаёт аккаунт, начальный аватар и сессию
одной транзакцией; 201 Me уже содержит выбранный avatarUrl. Без выбора/null —
NONE/EMPTY/0, с допустимым ID — PRESET/APPROVED/1. Неизвестный ID даёт 422 без
частичного создания; собственный SVG прикрепляется позже в профиле.
Прежний запрос с одним именем остаётся допустимым, новых операций нет.
Путь и ограничения демовхода — [регистрация](../../docs/product/registration.md).
Версия 0.9.0 по DEC-12 требует непустой presetId в регистрации;
старый запрос без выбора/null больше не допускается. Пустой каталог блокирует
регистрацию, демовход доступен. По DEC-13 добавлены adminGetDemoState и
adminResetDemoData: ADMIN/DEMO_MODE/Origin/подтверждение, версии и resetId,
атомарный штатный сид и завершение всех сессий. DemoResetReceipt сохраняется
в технической demo_state, потерянный ответ проверяется после нового входа.
Общий барьер транзакций передаётся исполнителям с BE-01/02. Правила —
[демосброс](../../docs/product/demo-reset.md), новых экранных URL нет.
Версия 0.10.0 по DEC-14 добавляет eventWindow=UPCOMING/STARTED_TODAY
и referenceTime в listMyParticipations, обязательный nullable referenceTime
в MyParticipationPage. При окне фильтрация PUBLISHED/времени и startsAt/event.id ASC
выполняются до пагинации; без окна прежний полный список по созданию записи.
Оба блока главной используют один опорный момент; курсор сохраняет его между
страницами. Это не снимок БД и не замена текущего now при бизнес-операциях.
Новых операций/схем/таблиц нет. Правила — [личная главная](../../docs/product/home-proposal.md).
Версия 0.11.0 по DEC-15 добавляет eventWindow=STARTED — все
начавшиеся PUBLISHED по startsAt/event.id DESC. «Участвую» по умолчанию использует
UPCOMING; «Все записи» без окна сохраняет ограниченные снятые публикации.
По DEC-16 после входа/регистрации без returnTo открывается персональная главная /;
это поведение веба, ответы auth не меняются. Новых операций/схем/таблиц нет.
**Версия 0.12.0** по DEC-18 добавляет listMessages.order:
интерфейс запрашивает NEWEST_FIRST (DESC), курсор ведёт к более ранним сообщениям,
API default OLDEST_FIRST (ASC) сохранён. adminListMessages остаётся ASC.
По DEC-19 listEvents получает dateFrom/dateTo: местные календарные даты каждой
встречи, [dateFrom,dateTo), вместе с абсолютными from/to через AND до LIMIT.
Новых операций/схем/таблиц нет. Исправлены одинаковые ID двух разных сообщений
в публичном/административном примерах. Валидатор теперь запрещает дубли ID в
списках и расхождение одноимённых OpenAPI/HTTP-примеров.
**Текущая версия 0.13.0**, DEC-20/21: login/register email/пароль вместо трёх
demo-маршрутов; JWT-cookie + sessions/ACTIVE в БД, ADMIN-блокировка USER.
AdminAccount/AccountStatusInput, три административные операции, isBlocked
публичного аккаунта и ownerIsBlocked организатора-организации/публичной организации;
Me содержит приватный email. Контент/участие/допуск сохраняются.
Правила — [вход](../../docs/architecture/authentication.md) и
[блокировка](../../docs/product/account-blocking.md). Старые ограничения нового
профиля без повторного входа заменены, пароль теперь проверяется сервером.
Модели и ограничения нужно брать из 0.13.0; потребители прежних версий требуют
согласованного обновления. Инструменты генерации не менялись.
Менять название/тип/обязательность
поля, URL, статус, права или поведение повтора независимо в одном приложении нельзя.
Координатор изменяет спецификацию, примеры и правила вместе, повышает версию и
сообщает затронутым исполнителям до интеграции. Ни бэкенд, ни фронтенд не ведут
вторую независимую копию API.

Подготовка контракта не запускает агентов и не означает разрешения на публикацию,
коммит или push. Результаты проверки инструментов — [в отчёте](../../docs/contracts/validation.md).
