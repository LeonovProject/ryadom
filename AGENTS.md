## Совместная работа

- Актуальный процесс — `docs/development/handoff/work-packets.md`, принят
  пользователем 20 октября после BE-03. Пакет из 2–3 связанных карточек, одна
  ветка/worktree, небольшие коммиты по карточкам; следующая карточка назначенного
  пакета не требует отдельного согласования/merge. Интеграция в конце пакета.
  Старые указания ниже/в исторических отчётах о каждой карточке заменены этим.
- BACKEND сам подключает модули в cmd/api/main.go; единственный DATABASE ведёт
  SQL/sqlc. FRONTEND сам подключает экраны/навигацию/кеш в своей стороне.
  Координатор не редактирует эти подключения параллельно. Общие контракты,
  зависимости, Compose, бренд и корневые документы остаются у COORDINATOR.
- Координатор принимает подтверждённые проверки исполнителя с привязкой к SHA;
  повторяет затронутые интеграционные проверки, полный набор — по конкретной
  причине. Досрочная передача нужна при блокировке другой стороны, изменении
  общего контракта/общих зависимостей или пересечении файлов.

- При параллельной разработке следуйте
  `docs/development/multi-agent-workflow.md`: одна задача, один владелец и
  явно ограниченный набор файлов. Используйте отдельные Git worktree и ветки,
  когда среда это поддерживает; общую рабочую копию делите только по непересекающимся файлам.
- Назначайте ограниченные пакеты карточек из `docs/development/tasks/README.md`,
  не весь backlog одним промптом. Для каждой карточки нужны результат,
  разрешённые файлы, подтверждённые зависимости и приёмка. После S1–S6 проверяйте совместную работу;
  отдельный мок или код без проверки не закрывает сценарий.
- До работы согласуйте контракт и владельца общих типов, API, миграций,
  зависимостей и параметров оформления. Изменения контракта передавайте
  зависимым исполнителям до интеграции.
- Не начинайте изменение файла, который уже закреплён за другим исполнителем.
  Сообщите координатору о пересечении; продолжайте независимую часть задачи.
- `README.md`, `CONTEXT.md`, очередь задач и общие конфигурации обновляет
  координатор интеграции. Передавайте ему необходимые изменения в итогах задачи.
- Не делегируйте просто ради количества агентов. Параллельные задачи должны
  иметь независимый результат и понятные границы.
- Не выполняйте push, публикацию, развёртывание или переписывание общей истории
  без соответствующего запроса пользователя. Ранее данное разрешение учитывается.

## Продукт и дизайн

- Шесть сценариев и дополнительный обязательный административный контур
  описаны в `docs/product/acceptance.md`. Не ограничивайте приёмку шестью строками.
- Три роли: пользователь, организация/сообщество, администратор. Организатор —
  автор события. Обязательны оба режима записи, внутреннее обсуждение, причины
  отказа организации и модерации события, модерация одного сообщения.
- Пользователь публикует от себя; организация — после допуска без повторного
  согласования события. Снятое/удалённое событие недоступно для новой записи
  даже по прямой ссылке. Имитация разрешена для входа, не для бизнес-операций.
- Обязателен адаптивный веб. Нативное приложение — идея команды; само по себе
  оно не даёт дополнительных баллов. Универсальность проверяется разными видами спорта.
- Организация, публикация встречи и участие человека имеют независимые статусы.
  Снятие с публикации не приравнивайте к отмене или удалению.
- Используйте брендбук 1.2. Исходные значения оформления —
  `brandbook/assets/tokens.json`; подписи состояний — `states.json`, тексты —
  `copy.ru.json`. Проверяйте соответствие текста фактическому поведению.
- При изменении материалов обновляйте исходник сборки, производные CSS/TS,
  ZIP и документы в составе одной согласованной задачи. Не меняйте бинарные
  документы одновременно несколькими агентами.

## Проверка и передача

- Выполните `python3 scripts/check_repository.py` и `git diff --check`.
  Для изменений локального макета проверьте синтаксис JS и выполните
  `node scripts/check_prototype.cjs` при наличии Node.js. Это имитация DOM,
  а не браузерная или техническая приёмка; проверку вида выполняйте отдельно.
  Для кода приложения дополнительно используйте документированные проверки
  затронутого модуля, когда они появятся, и обязательную контейнерную приёмку.
- При изменении API выполните `scripts/check_api_contract.py` в окружении с
  `scripts/requirements-contracts.txt`, обновите примеры и проверьте генерацию
  для Go и TypeScript по `packages/contracts/README.md`. Координатор владеет
  спецификацией и версией; изменения передаются зависимым исполнителям до интеграции.
- Для DOCX/PDF после изменений вёрстки выполните рендер и просмотрите все
  страницы; порядок описан в `brandbook/README.md`.
- В результате укажите изменённые файлы, проверки и их результат, изменения
  общих контрактов и оставшиеся ограничения. Не называйте просмотренный
  макет работающей функцией.
- Коммит должен содержать только относящиеся к задаче проверенные изменения.

## Code Review Rules

- Отмечайте смешение статусов организации, публикации и участия, а также
  подтверждение успеха без подтверждённого результата операции.
- Отмечайте расхождение текстов, цветов и размеров с общей системой, нарушение
  доступности и несогласованные изменения контрактов между модулями.
- Проверяйте, что повторная отправка заявки и неопределённый сетевой результат
  не создают дубли участия, когда соответствующая функция будет реализована.
