- [Проверки миграций](tests/migrations_test.go) и [ограничений](tests/constraints_test.go): реальная PostgreSQL и CLI goose, без подмены миграционного движка.

Требуемая версия для конфигурации BE-01/OPS-01:

```text
DATABASE_SCHEMA_VERSION=2026102001
```

Goose отдельно ведёт `goose_db_version`; она не входит в 11 таблиц приложения.
Обычный Up создаёт только пустую предметную схему и техническую строку
`demo_state.id=1` со случайным generation. Аккаунты/демоданные/сессии не создаются.
Повторный Up не перезаписывает generation, квитанцию или предметные данные.
Миграция не запускается из HTTP-сервера автоматически.

## Решения схемы

UUID по умолчанию выдаёт встроенный `gen_random_uuid()`. Значения состояний
хранятся как TEXT с CHECK; допуск организации существует только в её заявке,
публикация — во встрече, участие — в отдельной записи.

- `accounts`: уникальный канонический ASCII email, password_hash, USER/ADMIN,
  ACTIVE/BLOCKED, revision и согласованные поля блокировки. ADMIN только ACTIVE.
- `account_avatars`: один текущий источник NONE/PRESET/CUSTOM, отдельные статус
  и revision, согласованность SVG/готового ID/дат/проверяющего. Для статического
  preset_id нет FK: исключённый из manifest ID может сохраняться в аккаунте.
- `sessions`: UUID/jti, уникальный SHA-256 в нижнем hex, целые секунды created_at
  и ровно 24 часа до expires_at. Исходный JWT в таблице не хранится.
- `organization_applications`: одна заявка на профиль; отказ требует непустую
  причину, решение — дату и проверяющего. Отдельного дублирующего статуса в
  organizations нет.
- `activity_types`: единая уникальность normalized_name во всех состояниях,
  отдельные правила seed/пользовательского направления и решения. FK встречи
  не ограничивает использование направлений значением APPROVED.
- `events`: ровно один организатор; у личной встречи он совпадает с создателем.
  Снятие требует администратора, дату и непустую причину. `cover_svg` ограничен
  131072 байтами включительно, как личный SVG в account_avatars.
- `participations`: UNIQUE(event_id,account_id), независимый статус,
  согласованная пара полей решения. CONFIRMED допускается и без решения автора.
- `messages`: VISIBLE/HIDDEN, согласованные пары последнего скрытия/восстановления,
  неотрицательные версии модерации и жалоб. История последней пары сохраняется
  при обратном переходе, текущая видимость определяется статусом.
- `reports`: ровно одна настоящая FK-цель EVENT/MESSAGE, согласованное ручное
  решение и две частичные UNIQUE по аккаунту/цели, включая уже закрытые жалобы.
- `demo_state`: singleton ID, полностью пустая либо полностью заполненная
  квитанция; поколение до сброса отличается от текущего. На предметные аккаунты
  квитанция не ссылается.

Все FK используют ON DELETE RESTRICT. Индексы покрывают ведущие поля FK,
очереди, каталог, обсуждение, личные участия и открытые жалобы.
SQL ограничивает согласованность строки и связей; полная проверка email/PHC,
IANA-зоны, Unicode-нормализация направления, XML/SVG, роли проверяющего,
владение, переходы состояний и увеличение revision принадлежат общим серверным
модулям. Обязательное создание аккаунта/аватара/сессии одним commit — BE-02.
`updated_at` обновляет сервис при фактическом изменении; автоматического
триггера, меняющего дату при безопасном повторе, нет.

## Применение

Из корня репозитория, с уже настроенным DATABASE_URL целевой БД и установленным
закреплённым goose 3.29.0:

```bash
export GOOSE_DRIVER=postgres
export GOOSE_DBSTRING="$DATABASE_URL"
export GOOSE_MIGRATION_DIR=apps/api/db/migrations
goose -env=none validate
goose -env=none up
goose -env=none status
```

При обычной поставке используется схема public. Для отдельной схемы нужно
задать её в search_path соединения и GOOSE_TABLE=<schema>.goose_db_version.
Настройки CLI и формат миграций — [документация goose 3.29.0](https://github.com/pressly/goose/blob/v3.29.0/README.md).
Down удаляет таблицы этой миграции; это явный откат схемы, не сброс демоданных
DEC-13 и не действие обычного запуска.

## Выполненные проверки

В отдельном проекте `ryadom-db01`, без внешних портов и постоянного тома:

```bash
docker compose -p ryadom-db01 -f compose.foundation.yaml -f apps/api/db/migrations/testdata/compose.yaml build go-check
docker compose -p ryadom-db01 -f compose.foundation.yaml -f apps/api/db/migrations/testdata/compose.yaml up -d --wait db
docker compose -p ryadom-db01 -f compose.foundation.yaml -f apps/api/db/migrations/testdata/compose.yaml run --rm --no-deps go-check go test -race -count=1 ./...
docker compose -p ryadom-db01 -f compose.foundation.yaml -f apps/api/db/migrations/testdata/compose.yaml down
```

В этой среде стандартная сеть сборки Docker не разрешала proxy.golang.org.
Сборка успешно выполнена через следующую команду; запуск тестов оставался
в выделенной Compose-сети:

```bash
docker build --network=host -f apps/api/db/migrations/testdata/Dockerfile -t ryadom-db01-go-check .
```

Итоговый полный прогон Go с race detector прошёл. Проверки DB-01 выполнялись
без SKIP: validate, up/down/up, 11 таблиц без демосида, повторный up с сохранением
данных/квитанции/истории, откат всей миграции при конфликте в середине Up,
readiness 503 → 200 → 503 → 200, FK/индексы и положительные/отрицательные CHECK.
Проверено хранение встреч OPEN/APPROVAL и решений по участиям, отказ с причиной, невозможность дубля участия
при конкурентных вставках, уникальность закрытой жалобы, статусы/пары решений,
SVG 131072/131073 байта с ASCII и кириллицей, сохранение прежнего фона после
ошибочного изменения. Порядок DELETE из DEC-13 проверен только на SQL-фикстурах
в случайной тестовой схеме: `demo_state` сохранена. Это не реализация сброса.

Тесты создают случайные схемы и очищают только их. Для запуска этой группы
нужны RYADOM_MIGRATIONS_TEST_DATABASE_URL и CLI goose 3.29.0; overlay задаёт
адрес временной БД. Без этой переменной группа явно пропускается, поэтому
прежний прогон BE-01 без установленного goose сохраняет работоспособность.
Go-тесты находятся в tests/, чтобы goose validate видел в корне только миграции.

Локальные go test/go vet, check_repository.py, check_handoff.py, git diff --check
и отдельная проверка новых файлов также прошли. Локальный go test без явного
адреса не заменяет выполненный контейнерный прогон PostgreSQL.
